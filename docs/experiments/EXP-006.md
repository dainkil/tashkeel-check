# EXP-006 — 엔진 베이스라인: TTS 엔진은 걸프 인명을 얼마나 틀리게 읽고, 디아크리틱스·phoneme·사전을 주면 얼마나 고쳐지는가

- 날짜: 사전 등록 초안 2026-10-23. **실행하지 않았다.** 판정 기준·예산·엔진 목록은 사용자 확정 전이라 모두 [제안]이다.
- 확인할 질문:
  - Q1. 상용·오픈 TTS 엔진은 디아크리틱스 없는 걸프 인명을 얼마나 틀리게 읽는가(이름 단위 발음 오류율).
  - Q2. 정답 디아크리틱스를 붙여 주면 오류율이 얼마나 내려가는가. 엔진이 입력 디아크리틱스를 존중하는가.
  - Q3. phoneme(IPA·X-SAMPA)·사전·`customPronunciations`를 주면 더 내려가는가. 어느 엔진·모델·로케일이 그 입력을 실제로 받는가(존중 / 무시 / 오류).
  - 보조. 같은 입력을 3회 합성했을 때 청취 결과가 일치하는가.
- 비교 대상(조건) [제안]:
  - 엔진: Azure ar-SA(Hamed 또는 Zariyah), Azure ar-AE, Amazon Polly ar-AE(Hala 또는 Zayd), Google ar-XA Chirp 3 HD, ElevenLabs(v4 또는 Multilingual v2, 아랍어 음성 1개). 선택: 오픈 모델 1개(Habibi 또는 Chatterbox Multilingual, 로컬).
  - 입력 형식: I0 무디아크리틱스 원문 / I1 정답 디아크리틱스 텍스트 / I2 엔진별 발음 제어(Azure·Polly `<phoneme ipa>`, Google `customPronunciations`, ElevenLabs alias 또는 v4 인라인 IPA). I2를 받지 않는 엔진은 I2를 "미지원"으로 기록하고 건너뛴다.
  - 문장 틀: 이름을 콜센터 발화 틀 2개("안녕하세요, [이름] 님" / "[이름] 님의 예약이 확인되었습니다")에 넣어 합성한다. 이름만 따로 합성하지 않는다(문맥 없는 단어 읽기는 실제 사용과 다르다).
- 데이터·분할·표본 수 [제안]:
  - 1차: CamelProp(arXiv 2505.02656)에서 걸프 인명(국적·가문명 접두 ال·Wikidata 걸프 풀과 겹치는 것)을 걸러 150개. 라이선스·재배포 조건 확인 뒤 [미확인].
  - 2차(라벨러 확보 시): 자체 라벨 eval 150개([data.md 5.3절](../data.md)). 라벨러 2인 κ를 함께 보고.
  - 라벨러를 구하지 못하면 1차만으로 돌리고, 걸프 방언 독법(ق→g 등)은 재지 않는다고 적는다.
  - 이름 세트는 실행 전에 고정하고 해시를 `plan.json`에 둔다. 이 세트는 디아크리타이저·규칙 조정에 쓰지 않는다.
- 모델·코드·엔진·사전·설정 버전: 실행 때 엔진 모델 이름·음성·로케일·API 버전, 어댑터 버전, 디아크리틱스 정규형 규칙 버전, 평가표 버전, git 커밋을 기록한다. 고객 사전은 비운다(사전 효과는 I2로 본다).
- 실행 방법·장비·예산 [추정]:
  - 합성: 이름 150 × 문장 틀 2 × 입력 형식 최대 3 × 엔진 5 = 최대 4,500회(보조 반복 3회면 ×3). 글자 수 기준 과금이라 엔진 비용은 수 달러 수준이고 [추정], 무료 등급 한도 안에 들 가능성이 있다. 확인 뒤 적는다.
  - 청취: 아랍어 원어민 2인. 항목 하나에 약 15초로 보면 4,500항목 × 2인 ≈ 37.5시간 [추정]. 너무 많으면 (a) 엔진을 3개로, (b) 문장 틀을 1개로, (c) I0에서 두 청취자가 맞다고 한 이름은 I1·I2 청취를 생략하는 식으로 줄인다. 줄이는 규칙은 실행 전에 정한다.
  - ASR 왕복: 아랍어 ASR 1개(미정)로 전부 전사. 청취 전 선별과 일치율 보고.
- 지표 정의(실행 전 고정): [evaluation.md](../evaluation.md) 6.1(이름 단위 발음 오류율, 사람 청취 객관식, 2인 일치), 6.2(ASR 왕복 선별), 6.5(엔진 지원 매트릭스 판정: 존중 / 무시 / 오류), 6.9(반복 간 일치), 6.11(짝지은 부트스트랩 95% 구간, 이름 단위 재추출).
- 판정 기준(실행 전 고정, 지금은 [제안]):
  - **앞단 층의 가치:** 어느 엔진에서든 I0 오류율이 5% 이상이면 "앞단 층이 할 일이 있다". 모든 주요 엔진의 I0 오류율이 5% 미만이면 ADR-023 재검토(제품 가치 재검토).
  - **디아크리틱스 존중:** I1 − I0 오류율 차이의 짝지은 95% 구간이 0 아래에 있으면 그 엔진은 "디아크리틱스 존중". 구간이 0을 포함하면 "무시". 요청 거부·무음이면 "오류".
  - **phoneme·사전 존중:** I2 − I1을 같은 방식으로.
  - **1차 엔진 선택 근거:** I1 또는 I2 오류율이 가장 낮고 "존중" 판정인 엔진. 로케일(사우디·UAE)별로 따로 본다.
  - 기준 5%는 외부 근거가 없는 판단값이다. 사용자가 바꿀 수 있고, 바꾸면 실행 전에 적는다.
- 실행 뒤 확인(사전 등록): 청취자가 갈린 항목(`arguable`) 전부와 ASR 왕복이 청취와 다른 항목 50개를 작업자가 다시 듣고 평가표 문제가 있는지 본다. 평가표를 고치면 재채점 값을 나란히 보고하고 판정은 사전 등록한 평가표로 낸다.

- 해석과 한계(미리 적어 두는 것):
  - 이름 세트는 공개 인물 위주다. 고객 이름 분포로 일반화하지 않는다.
  - 청취자 2인의 판단이 정답이다. κ가 낮으면 그 이름들은 `arguable`로 빼고 민감도 지표를 같이 낸다.
  - 엔진은 실험 뒤에도 바뀐다. 결과에는 날짜와 모델 이름을 붙이고, 매트릭스는 "그 날의 값"이다.
  - 정답 디아크리틱스(I1)는 이상적인 상한이다. 실제 앞단 층은 사전 적중일 때만 이 상한에 닿고, 미적중은 디아크리타이저(EXP-007)의 정확도에 묶인다.
- 다음 행동·계획 변경 여부: 결과에 따라 (a) 1차 엔진·로케일 선택, (b) [architecture.md 4.7절](../architecture.md) 매트릭스 갱신, (c) 5% 미만이면 ADR-023 재검토.
