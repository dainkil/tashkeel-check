## 6.1 EXP-001 — Q0: 분석기가 고유명사에서 내는 후보 (실제 데이터)

- **단위:** 정렬된 (아랍어 토큰, 실제 영문 표기 집합) 고유 쌍
- **정렬 규칙 v1:** بن/بنت ↔ bin/bint, ال+X ↔ Al X / Al-X / AlX / El X, عبد + X ↔ Abdul X / Abdel X / 붙여 쓴 형태. 아랍어 단위는 아랍 문자만 쓰고, عبد·أبو 접두는 양쪽에 같이 있어야 한다. 세부는 [data.md 5.1절](data.md)이다. 정렬하지 못한 이름은 빼고 개수를 보고한다.

| 지표 | 정의 |
| --- | --- |
| M1 | 분석이 0개인 토큰의 비율 |
| M2 | 토큰당 분석 수 분포 (0 / 1 / 2~5 / 6 이상) |
| M3 | 모호 판정 규칙([4.9절](architecture.md))으로 모호인 토큰의 비율 |
| M4 | noun_prop 분석이 하나라도 있는 토큰의 비율 |
| M5 | 분석기 후보의 로마자 가운데 하나라도 실제 영문 표기와 일치하는 토큰의 비율. 엄격 일치와, 걸프 방언 대응(ق ↔ g)을 허용한 일치를 따로 낸다 |
| M6 | 아랍어 토큰당 실제 영문 표기 수 분포와 2개 이상인 비율 |

- 이름 위치(이름 / 아버지 이름 / 가문명)별, 빈도 상위·하위별로 나눠 본다.
- 가설: 가문명(ال 접두)은 분석기 사전에 없는 경우가 많다 [가설]. 걸프 방언 발음을 따른 표기(예: القرق → Gurg)는 표준 아랍어 분석기 후보에 없다 [가설].
- **판단 기준(실행 전 사용자 확정):** M5(방언 허용)가 50% 미만이면 분석기를 이름 독법의 근거로 쓰지 않고 일반 단어 탐지기로만 쓴다. 이름은 LLM 추출과 외부 근거(단계 2)에 의존한다고 계획에 적는다.
- **규칙 버전:** 정렬 v1·일치 v1. dev 300개로 고친 뒤 고정했다(ADR-015). dev 값은 규칙을 고치는 데 쓴 값이라 측정 결과로 보고하지 않는다.
- **결과 [확인, main 1회]:** 단위 3,023개, M5 엄격 0.500, 방언 허용 **0.502**로 기준을 넘었다. 다만 단위 부트스트랩 95% 구간(0.485~0.519, 사후)이 0.5를 포함한다. 가문명 0.418, 이름 0.705, 가운데 이름 0.533이다. 상세는 [EXP-001 기록](../../experiments/EXP-001.md)에 있다.

## 6.2 EXP-002 — Q1~Q3: 조건 비교 (합성 문서, 보류)

**상태:** 120/360회에서 보류했고 판정은 없다([EXP-002 기록](../../experiments/EXP-002.md)). 지시문 p0, 근거 검사 v1, 일치 규칙 v1로 고정한다(`exp002.SPEC`).

**정답 기준:** 고유명사가 나올 때마다, 문서 안 근거가 있으면 기대 처분은 근거 채택(인용 포함), 없으면 보류다. 일반 단어의 정답 독법은 아랍어 검수자 없이 정할 수 없으므로 처리 여부만 센다.

| 지표 | 정의 | 조건 |
| --- | --- | --- |
| 몰래 정함 비율 (합격선 지표) | 근거 없는 고유명사 가운데 말없이 찍었거나 근거 없이 확정한 비율. C0에는 확정 형식이 없어 말없이 찍음과 같다 | C0~C3 |
| 말없이 찍음 비율 (주 지표) | 근거 없는 고유명사 가운데 표시도 보류도 없이 하나로 옮긴 비율 | C0~C3 |
| 근거 없는 확정 비율 | 항목은 냈지만 근거 없이 `adopt`한 비율 | C1~C3 |
| 보류율 | 근거 없는 고유명사 가운데 보류한 비율 | C1~C3 |
| 근거 채택 검증 통과율, 근거 검증 실패 수 | 문서 안 근거가 있는 고유명사에서 | C1~C3 |
| 미처리 수 | 정답 고유명사와 분석기 모호 토큰(중립 토큰 제외) 가운데 처분이 없는 것. **이름 미처리(`n_unprocessed_names`)가 G1 지표이고 일반 단어 미처리(`n_unprocessed_ambiguous_words`)는 보조다.** 모호 판정 규칙이 문맥으로 풀리는 일반 단어를 많이 잡기 때문이다(ADR-014) | C1~C3 |
| 과잉 표시 토큰 수 | 고유명사도 분석기 모호 토큰도 하나도 덮지 않는 항목이 덮은 토큰 수(중립 토큰 제외). 항목을 쪼개거나 묶어도 값이 같다(ADR-014) | C1~C3 |
| 고확신 무근거 확정 토큰 수 | 확신도 0.8 이상 [확정]으로 근거 없이 확정한 토큰 수. 한 토큰을 여러 항목이 덮으면 고유명사 항목을 대표로 판정한다(ADR-014) | C1~C3 |
| 보류 후보 적중률 | 근거 없는 이름 가운데 보류한 토큰에서, 보류 항목의 후보에 문서가 실제로 쓴 표기(`english_used`, 신분증 표기 역할)가 든 비율. 담당자가 후보에서 고르기만 하면 되는지를 본다(G5, ADR-014) | C1~C3 |
| 문서 내 표기 불일치 수 | 같은 정규화 아랍어 이름이 서로 다른 표기로 옮겨진 경우 | C0~C3 |
| 도구 사용 | 호출 수, 모호 토큰 중 조회된 비율, 조회한 토큰 중 모호 토큰 비율 | C2 |
| 비용·지연 | 입력·출력 토큰, 실행 시간, 문서당 | 전체 |
| 반복 간 일치율 | 같은 문서 3회 실행의 처분 일치 | 전체 |

- **C0 판정 규칙 v0(실행 전 고정):** 번역문에 그 이름의 후보 표기가 둘 이상 나오거나 불확실 표시("[?]", "or", "/" 등)가 붙어 있으면 표시한 것으로 본다. 후보 표기는 분석기 로마자와 Wikidata 표기의 합집합이다. 자동 판정 결과 20건을 사람이 확인한다. 이 확인은 영어 번역문만 보면 되고 아랍어 검수가 아니다. 이것도 할 수 없으면 자동 판정 결과만 보고하고 그 한계를 적는다.
- **분해:** Wikidata 표기가 2개 이상인 이름과 1개인 이름, 분석기 분석이 0개인 이름과 1개 이상인 이름을 나눠 본다.
- **보고:** 조건별 값과 반복 간 범위를 함께 낸다. 표본이 작으면 그렇게 적는다. 문서 단위 부트스트랩 95% 구간(같은 문서를 함께 뽑는 1,000회)을 같이 낸다.
- **판정(실행 전 사용자 확정, `exp002.PASS_BAR`·`judge`):** 합격선은 몰래 정함 비율 ≤ 0.10, 근거 없는 확정 비율 ≤ 0.02, 근거 채택 검증 통과율 ≥ 0.90이다(eval 30개 × 3회 합산). C1이 합격하면 `stop`("지시만으로 충분")이다. C1이 불합격이고 C2나 C3가 합격하며, C1이 못 넘은 기준마다 차이의 95% 구간이 그 조건이 나은 쪽에서 0을 넘으면 `pass`다. 그 밖은 `fail`이다. 기준값은 외부 근거가 없는 판단값이다. 조건 쌍(C0−C1, C1−C2, C1−C3)마다 합격선 지표와 말없이 찍음 비율의 차이와 짝지은 부트스트랩 구간을 같이 낸다.
- **해석:** Q1은 C0의 말없이 찍음 비율, Q2는 C1 대 C0, Q3는 C2·C3 대 C1이다. 전부 보류해서 지표를 맞추는 경우는 과잉 표시 토큰 수와 근거 채택 검증 통과율로 드러난다.

## 6.3 실행마다 기록할 것

LangSmith 메타데이터와 로컬 `run_meta.json`에 같은 값을 남긴다: 조건, 모델 ID·버전, 프롬프트 해시, 문서 ID, seed, 분석기·DB 버전, 탐지 후보 수, 처분별 개수, 미처리 수, 분석기가 후보를 못 낸 고유명사 수, 툴 호출 수, 토큰 사용량, 실행 시간. ## 6.4 EXP-003 — 어려운 시험지에서 99% 기준 (ADR-017)

**단위:** 이름 부분(given·father·grandfather·ggf·family)이 나올 때마다 하나로 센다. 토큰 둘인 부분(عبد الله·آل X)도 하나다. 기대 처분은 5.3절 정답 규칙으로 정한다.

**엄격 철자(`romanize.strict_key`, 버전 s1):** 대소문자·공백·하이픈·아포스트로피·MRZ `<`·연결어(bin·bint·binti·ibn)만 무시하고 나머지 글자는 그대로 비교한다.
- 같은 철자: Al-Hashimi = AL HASHIMI = Alhashimi
- 다른 철자: Hamad ≠ Hamed ≠ Hammad, El Hashimi ≠ Al Hashimi, Saad ≠ Sa'd

**근거 검사 v2(`reconcile.verify_evidence(rule="v2")`):**
- 인용이 그 구간에 그대로 있어야 한다(v1과 같다).
- 채택 표기는 단어 묶음마다 인용 안 단어열과 엄격 철자가 같아야 하고, 순서는 따지지 않는다(`AL MUSLIM, Salem`에서 `Salem Al Muslim`).
- 실패하면 보류로 강등한다. gold를 보지 않는 검사다.

**오류 종류(`scoring_v2`, 채점 v2).** 한 부분에는 오류를 하나만 매긴다. 대표 항목은 EXP-002와 같이 고유명사 항목을 먼저 고른다.

| 종류 | 뜻 | 안전 오류 | 엄격 오류 |
| --- | --- | --- | --- |
| `unprocessed` | 그 부분의 토큰을 덮는 유효 항목이 없다 | O | O |
| `unsupported_no_evidence` / `_decoy` / `_other_person` / `_own_insufficient` | 기대 보류인데 근거 채택. 인용한 곳이 어느 표기도 아님 / 회사명·이메일·URL / 다른 사람의 표기 / 그 사람의 표기지만 그 부분의 철자가 없거나 충돌 | O | O |
| `unsupported_adopt`, `unsupported_word_adopt` | 고유명사를 근거 없이 `adopt`, 이름을 word 항목으로 `adopt` | O | O |
| `wrong_spelling` | 확정했지만 확정 문자열에 기대 표기가 엄격 철자로 없다 | O | O |
| `decoy_evidence_correct_spelling` | 철자는 맞지만 인용한 곳이 그 부분의 근거 표기가 아니다(출처가 거짓) | O | O |
| `translation_unmarked` | 항목은 보류(또는 강등)인데 번역문에 표시 없는 한 표기를 썼다. 기대 확정이고 그 표기가 기대 표기면 오류가 아니라 아래 `hold_instead_of_adopt`다 | O | O |
| `translation_wrong_spelling` | 맞게 확정했지만 번역문의 철자가 기대 표기와 다르다 | O | O |
| `hold_instead_of_adopt` | 확정해야 할 것을 보류했다 | | O |
| `translation_missing` | 맞게 확정했지만 번역문에서 그 표기를 찾지 못했다 | | O |

- **안전 정확도** = 안전 오류가 없는 부분 / 채점 부분. **엄격 정확도** = 오류가 없는 부분 / 채점 부분.
- **번역문 판정 규칙 t2:** 그 부분의 후보 표기를 그 구간 번역문에서 찾는다(C0 판정 규칙의 단어열 찾기).
  - 후보 표기는 걸러 낸 표기, 신분증 표기, 기대 표기, `must_include`, 분석기 로마자, 그 부분만 덮는 항목의 후보다. Wikidata 별칭 원본은 옆 이름과 맞아서 넣지 않는다.
  - 같은 구간의 다른 이름 부분이 자기 표기로 쓰인 자리 안에 걸린 후보는 이 부분의 표기로 세지 않는다(t2).
  - 서로 다른 표기가 둘 이상이거나 표시가 붙어 있으면 표시한 것으로 본다.
  - 표시 판정은 C0 판정 규칙 v0과 같되, 괄호 경계 너머의 표시(`[Sultan/?] Al Kuwaiti`의 `?`)는 옆 이름의 것으로 보고 세지 않는다. 이름 바로 옆의 `(?)`·`[?]`는 표시다. 단어 표시(`or` 등)는 원문에서 온전한 단어일 때만 센다(t2).
  - t1과 다른 점(eval 생성 전에 고침): 이름 앞 세 글자 창(`Suroor Khaled`의 `or `)이 단어 `or`로 잡히던 것과, 분석기 로마자(`Al-M'adyd`)가 옆 이름(`Abdel Aziz`의 `Aziz`)과 맞아 표기 둘로 세던 것을 고쳤다. 정답대로 답하는 가짜 응답기의 C0가 445/447에서 447/447이 됐다.
  - 후보를 하나도 찾지 못하면 `translation_not_found`로 두고, 오류가 아니라 감사용으로 센다[실행 전 고정].
  - 확정한 부분은 구간 번역문에 기대 표기가 엄격 철자로 있는지만 본다.
  - 근거: EXP-002 반복 1회의 C1~C3 번역문에서 보류 이름 523건이 모두 `[A/B]` 꼴이거나 표시가 붙어 있었다[확인].
- **C0 판정 규칙 v1:**
  - 표시한 이름은 보류로 본다.
  - 표시 없는 한 표기는 확정으로 보고 엄격 철자로 판정한다. 기대 보류면 `silent_pick`, 기대 확정인데 철자가 다르면 `wrong_spelling`이다.
  - 찾지 못한 이름은 `not_found`로 v0과 같이 안전 오류다.
  - C0는 판정에 쓰지 않고 Q1로 보고한다.
- **보조 지표(판정에 쓰지 않음):**
  - 민감도: arguable을 뺀 두 정확도
  - 문서 단위: 문서 안 부분이 전부 맞은 비율
  - 후보 완전성: 보류한 충돌 부분의 후보에 두 철자가 다 든 비율(`hold_must_include_rate`)
  - 일반 단어 쪽 토큰을 이름으로 표시한 비율(`lookalike_flag_rate`)
  - 사람·부분 기준 표기 불일치 수(`n_person_inconsistent`)
  - 유형별 두 정확도(`by_case_type`)
  - 오류 종류별 수
- **판정(실행 전 고정, `exp003.PASS_BAR`·`judge`):**
  - 조건마다 두 정확도의 점추정(eval 70개 × 반복을 합친 값)이 모두 0.99 이상이면 그 조건이 합격이다.
  - C1이 합격이면 `stop`이다.
  - C1이 불합격이고, C2나 C3가 합격하며 C1이 못 넘은 기준마다 C1 − 그 조건 차이의 95% 구간(같은 문서를 함께 뽑는 문서 단위 부트스트랩 1,000회)이 0 아래에 있으면 `pass`다.
  - 그 밖은 `fail`이다.
  - 참고 조건 C1p0(C1 + 옛 지시문 p0, 반복 1회)는 판정에 쓰지 않는다. "C1 − C1p0"(반복 1회끼리)를 참고로 보고한다(ADR-020).
- **단계적 반복(실행 전 고정, `exp003.stage_gate`, ADR-020):**
  - 반복 1회 뒤 C1·C2·C3의 두 정확도 점추정 6개 가운데 하나라도 [0.98, 0.995) 안이거나 값이 없으면 반복 2·3을 돌고, 아니면 반복 1회로 마친다.
  - 판단은 코드가 하고 기록 파일에 남긴다. 진행 확인에는 결정만 보인다.
- **"서비스 기준 99% 달성" 문구(`service_claim`):** 두 정확도 모두에서 아래 셋을 넘어야 한다.
  - 점추정
  - 반복마다의 한쪽 95% Clopper–Pearson 하한 중 가장 낮은 값
  - 문서 단위 부트스트랩 한쪽 95% 하한(5백분위수)
  - 기준은 셋 다 0.99다.
  - 근거: Clopper–Pearson은 부분들이 서로 독립이라고 가정해, 오류가 사람·문서에 몰리면 실제보다 좁다. 그래서 부트스트랩 하한을 같이 본다.
  - 오류 0개일 때 하한이 0.99를 넘는 최소 표본은 300개다. 1,000개면 오류 4개, 500개면 1개까지다[계산].
- **실행 뒤 확인(사전 등록, 아직 하지 않음):**
  - `uv run tashkeel exp003-errors`로 자동 판정 오류 전부와 정답으로 판정한 것 50개를 표로 뽑아 사람이 확인한다.
  - 99% 수준에서는 채점이 몇 건만 틀려도 판정이 바뀐다.
  - 채점 버그를 찾으면 `exp003-rescore`로 다시 채점한 값을 나란히 보고하고, 판정은 사전 등록한 채점으로 낸다.

## 6.5 묶음 검수 지표 (보류 기능, ADR-018)

묶음 검수는 ADR-021로 보류한 기능이다. 묶음 검수는 LLM 없이 결정적으로 도는 라벨 경로가 기본이라, 지표는 합성 묶음 사례와의 일치로 잰다. 가이드 14단계의 측정 항목을 아래처럼 둔다. 지금은 테스트(`tests/test_bundle_eval.py`)가 사례마다 상태·사유를 정답과 비교하는 것까지만 하고, 비율 지표는 실제 묶음 데이터가 생기면 센다.

## 6.6 조건 M2와 보관함 제안 지표 (ADR-022) [제안, 미측정]

조건 M2는 측정 없이 서비스 기본값이 됐다(사용자 결정 "실험은 빼고 완제품부터"). 아래는 나중에 잴 때 쓸 정의 [제안]이고, 지금 값은 테스트로 확인한 결정적 성질뿐이다. 판정 기준은 실행 전에 고정한다(6.4절과 같은 원칙).

| 지표 | 정의 | 지금 상태 |
| --- | --- | --- |
| 단일 문서 정확도(M2 대 C1) | synthetic-hard dev에서 채점 v2 엄격·안전 정확도. 보관함은 비운다 | 미측정. 두 agent가 일치해야 확정하므로 보류가 늘어 엄격 정확도가 내려갈 수 있다 [가설] |
| 보관함으로 자동 확정한 수 | 보관함 구절만으로 `final_decision`이 확정이 된 수 | 0 [확인, 테스트 `test_archive_pick_never_changes_a_decision_and_only_returned_hits_count`]. 구조상 중재자가 `archive`를 떼고 확정 규칙을 그대로 쓴다 |
| 다른 고객 서류 노출 수 | 다른 고객의 보관함 구절이 툴 결과·제안에 나온 수 | 0 [확인, 테스트 `test_customers_have_separate_archives`, `test_scope_of_one_customer_never_sees_another`] |
| 지어낸 구절·이번 서류를 제안한 수 | 툴이 돌려주지 않은 `hit_id`, 없는 구절, 이번 서류(ID·파일 해시)를 제안으로 낸 수 | 0 [확인, 테스트 `test_unverifiable_picks_are_dropped`, `test_reuploading_the_same_file_does_not_suggest_itself`] |

| 철자 충돌 표시율 | 지난 서류 둘의 철자가 다를 때 `archive_conflict`로 둘 다 보여 준 비율 | 미측정 |
| A0 대비 | 코드만으로 보관함을 조회해 제안을 낸 기준(LLM 0원)과 위 두 비율을 비교. M2가 잘못된 제안 비율에서 A0보다 낫지 않으면 agent가 비용만 늘린 것으로 본다 | 미측정 |
