**정렬 규칙 v0의 거르기 [확인, 구현]:** 별칭이 부분 이름이면 단위 수만 같고 엉뚱한 짝이 생긴다(예: الصباح ↔ "al Ahmad"). 그래서 이름 단위마다 영문 첫 글자가 아랍어 첫 글자(관사 뒤)와 대응해야 하고, 영문 표기는 두 글자 이상의 ASCII여야 한다. ASCII 조건은 여권 MRZ가 A~Z만 쓴다는 ICAO 자료를 따랐다 [문헌○]. 학술 음역("Makabūla")과 머리글자("M")는 이 조건으로 빠진다. 이 거르기가 EXP-001 결과에 주는 영향은 dev 표본에서 확인한다.

**정렬 규칙 v1 [확인, 구현, 2026-10-20, ADR-015]:** EXP-001 dev에서 v0가 받아들인 엉뚱한 짝을 보고 두 조건을 더했다. 아랍어 단위는 아랍 문자만 쓴다(아랍어 레이블이 라틴 문자인 Khaleghian ↔ Manager). عبد·أبو 접두는 양쪽에 같이 있어야 한다(إبراهيم ↔ Abu Aws, عبد العزيز ↔ Aziz, عبد الفتاح ↔ Ali). 아랍어가 عبدالنبي처럼 붙여 써도 접두로 본다. 한 사람의 정렬에서 짝 하나라도 걸리면 그 정렬 전체를 버리는 v0 방식은 그대로다.

주의:

- 공개 인물(왕족, 관료, 운동선수 등) 위주라 일반 고객 서류의 이름 분포와 다를 수 있다 [가설].
- 레이블이 그 사람의 여권 표기라는 보장은 없다. "실제로 쓰이는 영문 표기"로만 쓴다.
- 레이블에 직함("H.E. Dr")이나 설명("of Dubai")이 섞여 있다 [확인]. 정규화로 걷어 내고, 걷어 내지 못한 쌍은 정렬 실패로 센다.
- 회사명 조회는 하위 클래스를 따라가는 쿼리가 시간 초과(HTTP 504)로 실패했다 [확인]. 단순한 쿼리로 다시 시도하고, 안 되면 단계 1에서 뺀다.
- 개발용 표본(고정 seed, 토큰 300개 [제안])으로 정규화·정렬·`match_spelling` 규칙을 고친 뒤 고정하고, 나머지로 한 번만 측정한다. [확인, 2026-10-20] dev 300개로 v1을 고정했다. 규칙을 바꿔도 이미 본 dev 단위가 main으로 넘어가지 않게 dev 키 목록을 `data/wikidata/exp001_dev_keys.json`에 고정했다(ADR-015).

## 5.2 합성 문서: 실제 업무 규칙 기반

합성 문서는 아래 규칙만 반영한다. 출처가 없는 서식은 지어내지 않는다.

| ID | 규칙 | 출처 |
| --- | --- | --- |
| R1 | 위임장은 아랍어 또는 아랍어·영어 이중 언어로 쓰고, 분쟁 시 아랍어본이 우선한다 | [Virtuzone](https://virtuzone.com/blog/poa/), [ADGM 공증 FAQ](https://assets.adgm.com/download/assets/ADGM+Notary+Public+-+FAQs+23122024.pdf/295b27ce45cc11efb265024ee1b41222) [문헌○] |
| R2 | 위임인·대리인의 이름은 Emirates ID(거주자) 또는 여권(비거주자) 표기와 같아야 한다 | ADGM 공증 FAQ [문헌○] |
| R3 | 법인이 당사자면 상업 면허상의 상호, 법인 형태, 면허 발급 기관, 등록 번호, 주소와 서명자의 국적·신분증 번호·자격을 적는다 | ADGM 공증 FAQ [문헌○] |
| R4 | 걸프 인명은 이름 + بن/بنت + 아버지 이름 (+ 할아버지 이름) + 가문명(주로 ال 접두) 구조가 흔하다 | Wikidata 레이블 예: راشد بن حميد النعيمي [확인] |
| R5 | 같은 아랍어 이름에 영문 표기가 여럿 있다 | Wikidata 별칭 [확인], [ICAO 관련 자료](https://platform.keesingtechnologies.com/transliteration-of-arabic-in-mrtds/) [문헌○] |

- 상업 면허 인쇄 서식(필드 배치, 번호 형식)은 출처를 찾지 못했다 [미확인]. R3에 나온 필드만 쓴다.
- **생성:** 결정적 스크립트(seed 고정)가 템플릿에 5.1절 이름 토큰을 조합해 넣는다. 조합한 전체 이름이 Wikidata 레이블과 같으면 버린다. 실존 인물은 들어가지 않는다.
- **문서 유형:** 위임장(개인 위임인 → 대리인, 회사 관련 권한), 법인 당사자 정보가 들어간 확인서.
- **근거 배치 (synthetic-v1, ADR-014):** 이름의 영문 근거 줄(문서 안 근거)을 역할마다 붙인다. 위임장은 위임인·회사·대리인, 확인서는 회사·직원·서명자다. 문서마다 배치를 "없음(아랍어만)", "일부 역할만", "전부" 가운데 하나로 두고, 문서 유형마다 세 배치를 같은 수에 가깝게 나눈다. "일부 역할만"은 실제 서류 묶음에 신분증 표기가 있는 사람과 없는 사람이 섞인다는 가정에서 넣었다 [가설]. 실제 분포 자료가 없어 세 배치를 같은 수로 둔 것은 설정값이다 [제안].
- **구성 [확인, 2026-10-20 생성]:** eval 30개는 없음·일부·전부 각 10개, 근거 없는 이름이 든 문서 20개, 근거 없는 이름 61개(토큰 174개), 근거 있는 이름 토큰 151개. dev 10개는 4·4·2. 이전 synthetic-v0(문서 단위로 약 50% 이중 언어, `main` 59130fe까지)은 eval 30개 중 18개가 전부, 12개가 없음이었고 섞인 문서가 없었다.
- **synthetic-v2 [확인, 2026-10-20, ADR-015]:** 생성기 템플릿은 그대로이고 이름 풀을 정렬 규칙 v1로 다시 만들어 dev·eval을 같은 seed로 다시 생성했다. 문서 메타데이터에 풀의 정렬 버전(`name_pool_align_version`)을 적는다. 풀의 가중치가 바뀌어 이름이 바뀐 문서가 dev 8개, eval 21개다. 근거 배치와 위 개수는 그대로다. synthetic-v1 eval에는 v1에서 걸러지는 정렬에서 나온 정답 표기가 토큰 4개에 있었다(إبراهيم ↔ Abu Aws 2개, عمرو ↔ Amro 2개. Amro는 عبد الفتاح ↔ Ali로 잘못 정렬된 별칭에서만 나왔다).
- **정답 라벨:** 생성기가 함께 낸다. 이름 토큰 ID, 문서 안 근거 유무와 위치, Wikidata상 영문 표기 수, 분석기 모호 여부, 중립 토큰(지명·국가명·발급 기관·법인 형태).
- **표시:** 파일 머리와 메타데이터에 합성 데이터임을 적는다.
- **분할:** 개발용(프롬프트 디버깅, seed 1001)과 평가용(seed 2002)을 다른 seed로 만든다. 평가용은 조건 비교에 한 번만 쓴다. 개발 10개, 평가 30개 문서 [확정].
- **한계:** 템플릿의 아랍어 문장은 사람이 검수하지 않는다(팀 내 아랍어 검수자 [미확인]). 측정 대상이 이름이라 문장 오류의 영향은 제한적이라고 본다 [가설]. 결과는 "합성 문서 기준"으로만 보고하고 실제 서류 성능으로 일반화하지 않는다.

## 5.3 합성 묶음 (bundles-v1, 2026-10-21, ADR-018)

묶음 검수(단계 2)의 평가 사례다. 생성기 `src/tashkeel_check/data/bundles.py`(`uv run tashkeel make-bundles`)가 합성 문서 1개(`dev_001`, `eval_001`)의 정답 이름으로 묶음 JSON을 만든다. 형식은 가이드의 묶음 구조(`bundle_id`, `customer_id`, `entities`, `documents[document_id, document_type, segments[segment_id, text, entity_id, translated_name]]`)이고, 정답은 `gold{case, entity_type, review_items[{mention_id, status, reason}], …}`로 같은 파일에 두되 입력에서는 뗀다(`bundle.loader.split_bundle_gold`).

- **사례 9개(가이드 14단계 평가 사례):** `match`(일치→확정), `translation_mismatch`(불일치→대기), `no_english`(영문 근거 없음→대기), `conflict`(서류 간 표기 충돌→대기), `namesake`(같은 아랍어 표기·다른 대상 ID→연결하지 않음), `bad_quote`(원문에 없는 인용→거부. `gold.claimed_evidence`), `extraction_failed`(라벨 칸이 비어 있음→추출 실패 기록), `model_error`(LLM 호출 실패→실행 오류. `requires_llm`), `other_customer`(다른 고객 묶음에만 근거→쓰지 않음. 묶음 2개).
- **대상 종류 3개:** `person`(정답 이름의 비회사 역할), `organization`(회사 역할을 `شركة X للتجارة` / `X Trading Company`로), `other`(`مشروع X` / `X Project`, `entities`로 종류 지정). 같은 사례는 종류와 무관하게 같은 결과여야 하고 테스트가 이를 고정한다(`tests/test_bundle_eval.py`).
- **구성:** dev 30개, eval 30개(파일 이름 `{split}_{type}_{case}.json`). 계약서(`contract_001`: 안내 문장 + 라벨 칸 + 번역 표기) + 근거 서류(`evidence_001`: 종류별 `identity` / `commercial_register` / `registry_extract`, `라벨: 아랍어 | 영문 라벨: 영문`). 변이 표기는 정답 토큰의 `english_variants`에서 고른다.
- **손으로 만든 샘플:** `data/bundles/sample_bundle.json`(가이드 예시 `مسلم` / Muslim / Musallam + 회사 한 건). `data/bundles/sample/`의 txt 두 개는 ADR-007 검색 틀용이다.
- **한계:** 실제 KYC 묶음(상업등기 + 여권 MRZ + 정관)의 서식이 아니다. 대상 ID는 생성기가 붙이므로 "ID를 붙일 수 없는 실제 묶음" 비율은 알 수 없다[미확인]. 결과를 실제 서류 성능으로 일반화하지 않는다.
