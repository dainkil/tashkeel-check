- 이 문서: 데이터의 출처, 생성 규칙, 버전이다. 절 번호(5.1~5.4)는 코드 주석·ADR·실험 기록이 인용하므로 그대로 둔다. 문서 지도는 [docs/README.md](README.md).

## 5.1 실제 데이터: Wikidata 걸프 인명

| 항목 | 내용 |
| --- | --- |
| 조회 | SPARQL. 국적(P27)이 UAE·사우디·카타르·쿠웨이트·바레인·오만인 사람(Q5) 가운데 아랍어와 영어 레이블이 모두 있는 항목 |

| 이용 조건 | Wikidata 구조화 데이터는 CC0 [문헌○] |
| 용도 | EXP-001(Q0 실측), 합성 문서의 이름 토큰 풀 |
| 재현 | 쿼리 파일, 조회 날짜, 엔드포인트, 결과 스냅숏을 `data/wikidata/`에 저장. 나라별 원자료는 `raw/`에 캐시(git 제외) |

**정렬 규칙의 거르기(v0부터) [확인, 구현]:** 별칭이 부분 이름이면 단위 수만 같고 엉뚱한 짝이 생긴다(예: الصباح ↔ "al Ahmad"). 그래서 이름 단위마다 영문 첫 글자가 아랍어 첫 글자(관사 뒤)와 대응해야 하고, 영문 표기는 두 글자 이상의 ASCII여야 한다. ASCII 조건은 여권 MRZ가 A~Z만 쓴다는 ICAO 자료를 따랐다 [문헌○]. 학술 음역("Makabūla")과 머리글자("M")는 이 조건으로 빠진다.

**정렬 규칙 v1 [확인, 구현, ADR-015]:** v0에 두 조건을 더했다(EXP-001 dev에서 v0가 받아들인 엉뚱한 짝 때문). 아랍어 단위는 아랍 문자만 쓴다(아랍어 레이블이 라틴 문자인 Khaleghian ↔ Manager). عبد·أبو 접두는 양쪽에 같이 있어야 한다(إبراهيم ↔ Abu Aws, عبد العزيز ↔ Aziz, عبد الفتاح ↔ Ali). 아랍어가 عبدالنبي처럼 붙여 써도 접두로 본다. 한 사람의 정렬에서 짝 하나라도 걸리면 그 정렬 전체를 버리는 v0 방식은 그대로다.

주의:

- 공개 인물(왕족, 관료, 운동선수 등) 위주라 일반 고객 서류의 이름 분포와 다를 수 있다 [가설].
- 레이블이 그 사람의 여권 표기라는 보장은 없다. "실제로 쓰이는 영문 표기"로만 쓴다.
- 레이블에 직함("H.E. Dr")이나 설명("of Dubai")이 섞여 있다 [확인]. 정규화로 걷어 내고, 걷어 내지 못한 쌍은 정렬 실패로 센다.
- 회사명 조회는 하위 클래스를 따라가는 쿼리가 시간 초과(HTTP 504)로 실패했다 [확인]. 회사명은 Wikidata에서 받지 않는다([TS-001](troubleshooting.md)).
- 개발용 표본 300개로 정규화·정렬·`match_spelling` 규칙을 고친 뒤 고정했고, 나머지(main)로 한 번만 쟀다(EXP-001). 규칙을 바꿔도 이미 본 dev 단위가 main으로 넘어가지 않게 dev 키 목록을 `data/wikidata/exp001_dev_keys.json`에 고정했다(ADR-015).

## 5.2 합성 문서: 실제 업무 규칙 기반

합성 문서는 아래 규칙만 반영한다. 출처가 없는 서식은 지어내지 않는다.

| ID | 규칙 | 출처 |
| --- | --- | --- |
| R1 | 위임장은 아랍어 또는 아랍어·영어 이중 언어로 쓰고, 분쟁 시 아랍어본이 우선한다 | [Virtuzone](https://virtuzone.com/blog/poa/), [ADGM 공증 FAQ](https://assets.adgm.com/download/assets/ADGM+Notary+Public+-+FAQs+23122024.pdf/295b27ce45cc11efb265024ee1b41222) [문헌○] |
| R2 | 위임인·대리인의 이름은 Emirates ID(거주자) 또는 여권(비거주자) 표기와 같아야 한다 | ADGM 공증 FAQ [문헌○] |
| R3 | 법인이 당사자면 상업 면허상의 상호, 법인 형태, 면허 발급 기관, 등록 번호, 주소와 서명자의 국적·신분증 번호·자격을 적는다 | ADGM 공증 FAQ [문헌○] |
| R4 | 걸프 인명은 이름 + بن/بنت + 아버지 이름 (+ 할아버지 이름) + 가문명(주로 ال 접두) 구조가 흔하다 | Wikidata 레이블 예: راشد بن حميد النعيمي [확인] |
| R5 | 같은 아랍어 이름에 영문 표기가 여럿 있다 | Wikidata 별칭 [확인], [ICAO 관련 자료](https://platform.keesingtechnologies.com/transliteration-of-arabic-in-mrtds/) [문헌○] |

- 상업 면허 인쇄 서식(필드 배치, 번호 형식)은 출처를 찾지 못했다 [미확인]. R3에 나온 필드만 쓴다.
- **생성:** 결정적 스크립트(seed 고정)가 템플릿에 5.1절 이름 토큰을 조합해 넣는다. 조합한 전체 이름이 Wikidata 레이블과 같으면 버린다. 실존 인물은 들어가지 않는다.
- **문서 유형:** 위임장(개인 위임인 → 대리인, 회사 관련 권한), 법인 당사자 정보가 들어간 확인서.
- **근거 배치(synthetic-v1부터, ADR-014):** 이름의 영문 근거 줄(문서 안 근거)을 역할마다 붙인다. 위임장은 위임인·회사·대리인, 확인서는 회사·직원·서명자다. 문서마다 배치를 "없음(아랍어만)", "일부 역할만", "전부" 가운데 하나로 두고, 문서 유형마다 세 배치를 같은 수에 가깝게 나눈다. "일부 역할만"은 실제 서류 묶음에 신분증 표기가 있는 사람과 없는 사람이 섞인다는 가정에서 넣었다 [가설]. 실제 분포 자료가 없어 세 배치를 같은 수로 둔 것은 설정값이다 [제안].
- **구성 [확인]:** eval 30개는 없음·일부·전부 각 10개, 근거 없는 이름이 든 문서 20개, 근거 없는 이름 61개(토큰 174개), 근거 있는 이름 토큰 151개. dev 10개는 4·4·2.
- **synthetic-v2 [확인, ADR-015]:** 템플릿은 synthetic-v1과 같고, 이름 풀을 정렬 규칙 v1로 다시 만들어 dev·eval을 같은 seed로 생성했다. 문서 메타데이터에 풀의 정렬 버전(`name_pool_align_version`)을 적는다. 이전 판(v0·v1)은 git 기록에만 있다.
- **정답 라벨:** 생성기가 함께 낸다. 이름 토큰 ID, 문서 안 근거 유무와 위치, Wikidata상 영문 표기 수, 분석기 모호 여부, 중립 토큰(지명·국가명·발급 기관·법인 형태).
- **표시:** 파일 머리와 메타데이터에 합성 데이터임을 적는다.
- **분할:** 개발용(프롬프트 디버깅, seed 1001)과 평가용(seed 2002)을 다른 seed로 만든다. 평가용은 조건 비교에 한 번만 쓴다. 개발 10개, 평가 30개 문서 [확정].
- **한계:** 템플릿의 아랍어 문장은 사람이 검수하지 않는다(팀 내 아랍어 검수자 [미확인]). 측정 대상이 이름이라 문장 오류의 영향은 제한적이라고 본다 [가설]. 결과는 "합성 문서 기준"으로만 보고하고 실제 서류 성능으로 일반화하지 않는다.

## 5.3 어려운 합성 문서: synthetic-hard (EXP-003, ADR-017)

synthetic-v2는 근거가 늘 같은 사람의 영문 줄로 바로 옆에 있고, 사람끼리 이름이 겹치지 않고, 함정이 없다. 그래서 EXP-002에서 C1~C3가 모두 만점이었다(시험지가 쉬운 탓으로 본다[가설]). synthetic-hard는 실제 서류(위임장·고용 확인서·상업등기·의사록)에서 생길 법한 어려운 경우(동명이인, 다른 사람의 표기, 회사명·이메일 속 이름, 여권 MRZ, 이니셜 등)를 넣은 시험지와 답안지다. synthetic-v2(`data/synthetic/`)는 그대로 둔다.

- **생성기:** `src/tashkeel_check/data/synthetic_hard.py`, 버전 `synthetic-hard-v2`(2026-10-21 dev 실제 모델 점검 뒤 고침, 아래 "v2에서 바뀐 것"), gold 형식 2. 명령은 `uv run tashkeel make-synthetic-hard --split dev|eval`이고, 출력은 `data/synthetic-hard/{dev,eval}/`(`hdev_NNN.json`·`heval_NNN.json`)와 수량 보고 `quota_<split>.json`이다.
- **seed:** dev 3001, eval 4002. 문서마다 난수 흐름을 따로 쓰고(seed×10007+번호), 유형 배정표만 seed 하나로 만든다.
  - eval은 4002부터 차례로 시도해 최소 수량을 처음 채우는 seed를 쓴다(최대 20번). 고르는 기준은 수량뿐이고 모델 결과가 아니다. 쓴 seed는 문서 `meta.seed`와 `quota_eval.json`의 `seed`·`seed_tries`에 남는다. eval 생성 전에 정했다(2026-10-21).
- **문서 수:** dev 20개(프롬프트·형식 점검용), eval 70개.
- **eval 생성 원칙:** eval은 조건 비교에 한 번만 쓰고, 이미 있으면 다시 만들지 않는다(`--overwrite` 없이는 거부).
- **템플릿 4종(차례로 돌아감):**
  - 여권 칸이 있는 위임장
  - 고용 확인서(레터헤드에 회사 URL, 인사부 문의 이메일 `hr@<가문명>.example.com`)
  - 상업등기 발췌(파트너 7~9명. 관리자·서명권자 줄은 `المدير: الشريك رقم 5، السيد …`처럼 파트너 번호를 붙인다)
  - 총회 의사록(의장·أمين السر·참석자 4~6명, 결의 4건)
  - 이름 풀과 고정 목록(국적·도시·발급 기관)은 synthetic-v2와 같다. 이메일·URL은 예약 도메인 `example.com`·`example.net`만 쓴다.
- **이름 풀 정리:**
  - 같은 엄격 키의 변이를 합친다.
  - 최빈 표기와 일치 규칙 v1로 맞지 않는 Wikidata 별칭(أحمد→Ali, محمد→Mo 등)은 후보에서 뺀다.
  - 근거 표기로 쓰는 철자는 빈도 2 이상만 쓴다. nisba 가문명(الكويتي·القطري)만 빈도 1을 허용한다.
  - 띄어 쓰는 단위(عبد X, آل X, أبو X)를 살린다(synthetic-v2는 뺐다).
  - 관사 El은 풀에 빈도 2 이상인 것이 거의 없어, B5에서는 그 사람의 "Al X" 표기를 "El X"로 바꿔 쓴다.

### 정답 규칙 (실행 전 고정)

사람마다 이름 부분(given·father·grandfather·ggf·family)별로, **그 사람의 로마자 표기**에 나온 완전한 철자를 엄격 키(6.4절)로 모은다. 이니셜(`S.`)과 생략된 부분은 철자로 치지 않는다.

| 그 부분의 철자 | 기대 처분 |
| --- | --- |
| 하나 | 확정(adopt). 기대 표기는 그 철자, 근거는 그 철자가 든 표기 전부 |
| 둘 이상(같은 사람의 표기가 서로 다름) | 보류. 그 철자들을 모두 후보에 넣어야 한다(`must_include`, 엄격 정확도에는 넣지 않고 따로 보고) |
| 없음 | 보류 |

- **"그 사람의 표기"로 치는 것:**
  - 역할 라벨이 붙은 줄(`Principal:`, `Partner 3:`, `Attendee 2:` 등)
  - 그 사람의 여권 칸(`Surname: … / Given names: …`, MRZ 줄, `Passport name:`)
  - 라벨 없는 줄은 이름 전체가 다 있고, 같은 전체 이름을 가진 사람이 문서에 하나뿐일 때만 친다(서명 목록, 첨부)
  - 표기 하나는 구간 하나 안에 있다(출력 스키마가 구간 하나만 인용할 수 있다).
- **근거가 아닌 것:** 다른 사람의 표기(아랍어가 같아도), 회사명·이메일·URL 속 이름, 비슷하지만 다른 이름의 표기.
- **같은 사람의 재등장:** 짧은 형태(이름 + 가문명)나 칭호 + 이름으로 다시 나오면, 처음과 같은 처분을 따른다.
- **채점에서 빼는 토큰:** 칭호(الشيخ·الدكتور·المهندس 등)와 중립 토큰(법인 형태·발급 기관·도시·국가)은 이름 부분이 아니다. 같은 문서의 일반 단어 쪽(`صالح لمدة`, `حسن السيرة`, `كامل الأهلية`, `أمين السر`, `بشكل عادل`, `سليم` 술어)과 nisba와 같은 국적 형용사는 `lookalike_token_ids`로 따로 둔다. 정확도에는 넣지 않고, 이름으로 표시했는지만 보고한다.
- **판단이 갈릴 수 있는 정답(`arguable`):**
  - 아버지에게만 근거가 있는 아들의 가문명·아버지 이름
  - 충돌 표기가 있는 사람의 나머지 부분
  - 라벨 없는 먼 곳 표기만 있는 부분
  - 짧은 재등장
  - 주 지표에는 넣고, 뺀 민감도 지표를 같이 낸다.

### 유형과 eval 최소 수량 (이름 부분 기준)

유형 태그는 문서를 다 만든 뒤 gold에서 다시 계산한다. 한 이름 부분에 여러 유형이 붙을 수 있다.

| 묶음 | 유형 | 기대 처분 | eval 최소 |
| --- | --- | --- | --- |
| A 동명이인·겹침 | A1 같은 아랍어 이름(부자 가문명·아버지 이름 포함), 근거는 다른 사람에게만 | 보류 | 80 |
| | A2 같은 아랍어 이름의 두 사람이 서로 다른 영문 표기로 각자 근거가 있음(محمد → Mohammed / Muhammad) | 각자 자기 표기로 확정 | 60 |
| | A3 같은 사람이 짧은 형태·칭호로 다시 나옴 | 처음과 같음 | 100 |
| B 근거 형식 변형 | B1 전부 대문자 | 확정 | 60 |
| | B2 `AL-HASHIMI, Ahmed` 순서 또는 `Surname / Given names` 칸 | 확정 | 60 |
| | B3 여권 MRZ 줄(`P<AREAL<HASHIMI<<AHMED<SALEH<<…`, 44자. 넘으면 할아버지 이하를 뺀다) | 확정(빠진 부분은 보류) | 60 |
| | B4 이니셜(`A. S. Al Hashimi`) | 이니셜 부분 보류, 나머지 확정 | 40 |
| | B5 관사 El(`El-Hashimi`) | 그 형태로 확정(엄격 키에서 El ≠ Al) | 30 |
| | B6 아버지·할아버지 이름이 빠진 영문(`Saleh Al Fawzan`) | 빠진 부분 보류 | 50 |
| C 함정 근거 | C1 비슷하지만 다른 이름(아랍어 한 글자 차이, 일치 규칙 v1로는 같은 표기)을 가진 다른 사람의 표기만 있음 | 보류 | 50 |
| | C2 회사명·이메일·URL 속에만 그 가문명이 있음(가족 회사) | 보류 | 80 |
| | C3 같은 사람의 표기가 둘이고 그 부분의 철자가 서로 다름 | 보류, 두 철자 모두 후보 | 50 |
| D 규모·문맥 | D1 이름 부분이 30개 넘는 긴 문서(문서 단위) | — | 문서 15개 |
| | D2 같은 문서에 그 이름과 같은 일반 단어가 있음 | 이름은 규칙대로 | 이름 50 + 일반 단어 토큰 50 |
| | D3 칭호 옆의 이름, عبد/آل/أبو 단위, 긴 nasab(증조부) | 규칙대로 | 80 |
| | D4 라벨 없는 먼 곳 표기(서명 목록·첨부)만 근거 | 확정 | 60 |
| | D5 국적 형용사와 같은 가문명(nisba: الكويتي / كويتي الجنسية) | 규칙대로 | 20 |

- **함께 지킬 조건:**
  - 어려운 유형에 속한 이름 부분이 60% 이상이다. 계획은 70%였으나 생성기 구조상 약 2/3에서 멈춰 하한을 바꿨다. 나머지는 엄격 정확도에서 과잉 보류를 재는 쉬운 대조군이다.
  - 확정 비율은 40~60%다.
  - eval에서 최소 수량을 못 채우면 생성기가 멈춘다.
- **배정:** 앞쪽 절반의 문서는 모자란 유형에 가중치를 준 무작위로 고르고, 뒤쪽 절반은 가장 모자란 유형부터 채운다. 목표는 최소 수량의 1.35배다.
- **배정 조정:** dev와 별도 seed(9001~9020)로 eval 크기를 시험 생성하며 맞췄다. 어떤 모델도 이 문서를 보지 않았다. v2에서는 20개 중 14개가 최소 수량을 채웠고, 이름 부분 1,441~1,514개, 어려운 비율 0.63~0.66, 확정 비율 0.54~0.60이었다[확인]. 못 채우는 seed가 있어 위의 seed 넘김 규칙을 뒀다.
- **채점이 흔들리지 않게 하는 제약(`validate_doc`):**
  - 한 구간 안의 채점 대상 이름 부분끼리는 아랍어가 같거나 일치 규칙 v1로 맞는 표기를 갖지 않는다(번역문 판정이 섞이지 않게).
  - 짧은 재등장과 칭호 재등장은 한 사람만 가리킨다.
  - 라벨 없는 표기는 유일한 전체 이름이다.
  - MRZ는 44자다.
  - 확정 ⇔ 기대 표기 ⇔ 근거가 있다.
  - 모든 인용이 구간 안에 있고, 확정 부분마다 근거 검사 v2를 통과한다.
- **eval 구성 [고정, 2026-10-21 생성]:** 70개 문서(seed 4002, 첫 시도에서 최소 수량 충족), 이름 부분 1,457개(아랍어 토큰 1,573개), 어려운 비율 0.642, 확정 비율 0.566, arguable 518개, 긴 문서 24개. 문서 해시와 확인 내용은 EXP-003 기록에 있다. 다시 만들지 않는다.
- **dev 구성 [확인, 2026-10-21 v2로 다시 생성]:** 20개 문서, 이름 부분 447개(아랍어 토큰 473개), 어려운 비율 0.622, 확정 비율 0.568, arguable 164개, 긴 문서 8개. 문서 수로 줄인 최소 수량을 모두 채운다(dev는 강제하지 않고 eval만 강제한다). 유형별 수는 `data/synthetic-hard/quota_dev.json`에 있다. v1 dev(451개)는 실제 모델 점검에 쓴 뒤 바꿨다.
- **정답 규칙과 채점이 서로 맞는지 [확인]:**
  - 정답대로 답하는 가짜 응답기는 v2 dev 447개에서 C0~C3 모두 안전·엄격 정확도 1.0이었다(채점 v2, 번역문 판정 t2). t1에서는 C0가 445/447이었고, 그 두 건이 t2로 고친 채점 버그였다(평가 문서 6.4절).
  - 일부러 틀리는 응답기는 정해진 오류 종류를 정확히 그 수만큼 냈다. 예를 들어 기대 보류 193개를 근거 없이 확정하면 근거 없는 확정이 193개였다.
- **v2에서 바뀐 것(dev 실제 모델 점검 뒤 사용자 결정, EXP-003 기록):**
  - 고용 확인서의 문의처를 사람에서 인사부로 바꿨다. v1은 "문의는 OO 씨에게 아래 이메일로"와 개인 주소(`y.alhajri@…`)를 썼다. 모델은 지시문 p1의 원칙("문서가 그 사람의 것이라고 분명히 이어 주는 표기")대로 이메일에서 가문명을 확정했고, 정답 규칙("이메일은 근거 아님")과 갈렸다. 정답 규칙과 p1은 그대로 두고 문서가 둘을 잇지 않게 했다. 가문명이 회사명·URL·이메일 안에만 있는 함정(C2)은 남는다.
  - 상업등기의 관리자·서명권자 줄에 파트너 번호를 붙였다. v1에서 모델은 "관리자가 파트너 5라고 문서가 밝히지 않았다"며 짧은 재등장을 보류했고, 정답(같은 사람 → 같은 처분)과 갈렸다. 의사록의 결의 문장(참석자를 관리자로 임명 등)은 모델이 참석자와 이어서 바꾸지 않았다.
  - B6 사람 떼어 두기와 seed 넘김. v1에서는 상업등기의 쌍 유형(A1·A2·C1)이 사람을 둘씩 묶어 생략·이니셜 표기를 붙일 사람이 남지 않아 B6 미달이 잦았다(v1 커밋본은 시험 seed 10개 중 3개만 통과). v2는 B6를 고른 긴 문서에서 쌍을 만들기 전에 한 명을 떼어 B6에만 쓴다.
- **한계:**
  - 아랍어 문장과 단어 함정의 자연스러움은 사람이 검수하지 않았다(Claude가 dev를 읽어 확인, 사람 검수 아님).
  - 유형 구성(어려운 유형 약 2/3, 문서 유형 넷)은 설정값이다. 이 시험지의 99%는 이 구성에서 잰 합성 문서 결과이고, 실제 서류로 일반화하지 않는다.

## 5.4 합성 묶음 (bundles-v1·bundles-kyc-v1, 보류 기능, ADR-018)

묶음 검수(ADR-018, ADR-021로 보류)의 평가 사례다. 생성기 `src/tashkeel_check/data/bundles.py`(`uv run tashkeel make-bundles`)가 합성 문서 1개(`dev_001`, `eval_001`)의 정답 이름으로 묶음 JSON을 만든다. 형식은 가이드의 묶음 구조(`bundle_id`, `customer_id`, `entities`, `documents[document_id, document_type, segments[segment_id, text, entity_id, translated_name]]`)이고, 정답은 `gold{case, entity_type, review_items[{mention_id, status, reason}], …}`로 같은 파일에 두되 입력에서는 뗀다(`bundle.loader.split_bundle_gold`).

- **사례 9개(가이드 14단계 평가 사례):** `match`(일치→확정), `translation_mismatch`(불일치→대기), `no_english`(영문 근거 없음→대기), `conflict`(서류 간 표기 충돌→대기), `namesake`(같은 아랍어 표기·다른 대상 ID→연결하지 않음), `bad_quote`(원문에 없는 인용→거부. `gold.claimed_evidence`), `extraction_failed`(라벨 칸이 비어 있음→추출 실패 기록), `model_error`(LLM 호출 실패→실행 오류. `requires_llm`), `other_customer`(다른 고객 묶음에만 근거→쓰지 않음. 묶음 2개).
- **대상 종류 3개:** `person`(정답 이름의 비회사 역할), `organization`(회사 역할을 `شركة X للتجارة` / `X Trading Company`로), `other`(`مشروع X` / `X Project`, `entities`로 종류 지정). 같은 사례는 종류와 무관하게 같은 결과여야 하고 테스트가 이를 고정한다(`tests/test_bundle_eval.py`).
- **구성:** dev 30개, eval 30개(파일 이름 `{split}_{type}_{case}.json`). 계약서(`contract_001`: 안내 문장 + 라벨 칸 + 번역 표기) + 근거 서류(`evidence_001`: 종류별 `identity` / `commercial_register` / `registry_extract`, `라벨: 아랍어 | 영문 라벨: 영문`). 변이 표기는 정답 토큰의 `english_variants`에서 고른다.
- **손으로 만든 샘플:** `data/bundles/sample_bundle.json`(가이드 예시 `مسلم` / Muslim / Musallam + 회사 한 건). `data/bundles/sample/`의 txt 두 개는 ADR-007 검색 틀용이다.
- **KYC 묶음(bundles-kyc-v1, `src/tashkeel_check/data/kyc_bundles.py`, 같은 명령):** 사례마다 다른 합성 문서(`{split}_001`~`_008`)의 정답 이름(회사 1, 개인 2)으로 묶음 하나. 서류는 아랍어 상업등기 `register_001`(`اسم الشركة:` / `اسم المالك:` / `اسم المدير:` 칸 + 번역 표기, 검수 대상), 영문 여권 `passport_p1`·`passport_p2`(`Surname: | Given Names:` 인쇄 칸 + MRZ 첫 줄 `P<SAU…<<…` + 둘째 줄, 근거), 이중언어 정관 `aoa_001`(`اسم الشركة | Company Name`, `اسم الشريك | Shareholder`, 근거). 사례 8개: `match`(전부 확정), `passport_mismatch`(소유자 번역이 여권과 다름), `no_passport`(관리자 여권 없음→근거 없음), `passport_aoa_conflict`(여권·정관 영문이 다름→충돌), `namesake_shareholder`(정관의 다른 주주가 같은 아랍어 표기·다른 대상 ID→연결 안 함), `company_mismatch`(회사명 번역이 정관과 다름), `mrz_only`(여권에 인쇄 칸 없음→MRZ 해독으로 확정. 하이픈이나 39자 초과로 해독값이 다른 이름은 `gold.mrz_lossy`에 적고 대기가 정답), `unlinked_manager`(관리자 칸에 대상 ID 없음). dev 8개, eval 8개(파일 `{split}_kyc_{case}.json`, 같은 폴더). 정답은 생성기가 내고 테스트(`tests/test_bundle_eval_kyc.py`)가 커밋된 파일과 생성기 출력이 같은지도 본다.
- **한계:** 실제 KYC 서식이 아니라 칸 이름과 MRZ 규칙만 흉내 냈다(MRZ 검사 숫자는 만들지도 보지도 않는다). 대상 ID는 생성기가 붙이므로 "ID를 붙일 수 없는 실제 묶음" 비율은 알 수 없다[미확인]. 결과를 실제 서류 성능으로 일반화하지 않는다.
