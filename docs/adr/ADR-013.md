# ADR-013 — 단계 1.5 전에 동작을 보존하는 리팩토링을 하고, 골든 테스트·LLM 입력 해시·정적 검사·CI를 코드 품질 기준으로 둔다

- 날짜: 2026-10-20
- 상태: 채택
- 배경: 단계 1.5는 `runner`·`graph`·`reconcile` 결과·설정 위에 올라간다. 결과가 타입 없는 dict이고, 경로가 레포 위치에 묶여 있고, 예외 체계와 정적 검사가 없어 그대로 서비스를 붙이면 약점이 API 응답과 DB 스키마에 굳는다. EXP-002가 사전 등록돼 있어 LLM 입력이나 지표를 바꾸면 안 된다.
- 결정: 단계 1.5 전에 동작을 보존하는 리팩토링을 하고, 골든 테스트·LLM 입력 해시·정적 검사·CI를 품질 기준으로 둔다.
- 결정 이유: 골든과 해시 테스트가 있어야 "동작이 같다"를 측정으로 보일 수 있다(골든을 만들다 TS-003을 찾았다). 설정을 `BaseSettings`로 두면 CLI의 `load_dotenv`가 환경 변수에 써 넣은 값 때문에 테스트 결과가 실행 순서에 따라 달라진다.
- 고려한 대안: 서비스화부터 하고 나중에 정리 / 전면 재작성. 설정은 `pydantic-settings`(위 이유로 제외).
- 최종 결정:
  - 규칙: 골든 스냅숏을 먼저 만들고 리팩토링 중에는 다시 만들지 않는다. LLM 입력(프롬프트·스키마·툴 docstring·사용자 메시지)은 바꾸지 않고 해시 테스트로 지킨다. 커밋 하나에 한 종류의 변경만 넣고 기능은 더하지 않는다.
  - 기준: ruff(E,F,I,B,UP,SIM, 120자), mypy(`disallow_untyped_defs`), pytest, CI(live·camel 제외). 설정은 pydantic `BaseModel` + `load_settings()`, 결과는 `ReviewResult`로 검증한다(모르는 키는 오류). metrics는 dict로 둔다.
  - 영향: 개발 의존성 4개, 골든 약 4.9MB. 프롬프트·스키마를 바꾸면 해시 테스트도 고쳐야 하고, 골든을 다시 만드는 변경은 리팩토링이 아니므로 이유를 변경 이력에 적는다.
  - 재검토: 지표 정의가 EXP 전에 바뀔 때, metrics를 DB 열로 펼쳐야 할 때, CI에서 CAMeL DB를 받을 수 있게 될 때.
