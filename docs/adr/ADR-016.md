# ADR-016 — EXP-002를 멈췄다 이어서 할 수 있게 하고, 반복 → 문서 → 조건 순서로 동시에 돌리며, 중간 확인에는 사용량만 보인다

- 날짜: 2026-10-21
- 상태: 채택
- 배경과 문제: EXP-002(조건 4 × eval 30 × 반복 3 = 360회)를 실행하기 직전에 실행 방식의 문제 다섯 가지를 확인했다.
  1. `exp002.run`은 호출할 때마다 새 시각 폴더를 만들고 360회가 다 끝나야 `summary.json`을 썼다. 중간에 멈추면 처음부터 다시 돌아야 했다.
  2. 순서가 조건 → 문서 → 반복이었다. 비용 때문에 절반에서 멈추면 C2·C3가 0회라 비교할 수 없었다.
  3. 토큰은 실행별 `metrics.json`에만 남아, 돌아가는 동안 누적량과 예상 총량을 볼 수 없었다.
  4. `graph.agent`가 모든 예외를 잡아 `errors`에 남기므로, 한도 초과(429)·인증 오류 같은 API 오류도 모델 실패(`valid_output` 거짓)로 기록됐다. 크레딧이 떨어지면 남은 실행이 전부 실패로 채워질 수 있었다.
  5. 순차 실행이라 약 5시간이 걸릴 것으로 외삽했다.

  사용자는 중간에 멈춰도 이어서 할 수 있게 하고, 사용량을 중간중간 확인하며 조절하기를 원했다(2026-10-21).
- 검토한 대안:
  - (재개) 실행 폴더의 `metrics.json` 유무로 완료를 판단한다 / 완료 기록 파일을 따로 둔다.
  - (시간) 동시 실행 / OpenAI Batch API / 추론 강도 낮추기 / 반복 3 → 2 / 로컬 모델(Ollama).
  - (중간 확인) 결과 지표까지 보인다 / 사용량·진행만 보인다.
- 결정:
  - **재개:** 실행 폴더에 `plan.json`(문서 해시, 조건, 반복, 순서, 모델, 설정, 프롬프트 해시, 일치 규칙·분석기·패키지 버전)을 처음 한 번 고정한다. 실행이 하나 끝날 때마다 `runs.jsonl`에 한 줄을 덧붙인다(fsync).
    - `--resume`은 기록에 없는 실행만 돌린다. 설정이 `plan.json`과 다르면 이어 붙이지 않는다.
    - 세션마다 git 커밋과 패키지 소스 해시를 기록하고, 소스가 바뀌었으면 경고한다.
  - **순서:** 반복 → 문서 → 조건으로 바꾼다.
  - **동시 실행:** `--workers`. 첫 실행은 4개로 한다. 실행마다 모델과 그래프를 새로 만들고, camel-tools 호출만 잠금으로 하나씩 들여보낸다.
  - **멈춤:** 아래 중 하나에 걸리면 새 실행을 시작하지 않고, 돌던 실행만 마저 기록하고 멈춘다(종료 코드 4).
    - `--max-runs`, `--token-budget`(이번 세션 기준)
    - 실행 폴더의 `STOP` 파일
    - 첫 번째 Ctrl+C·SIGTERM. 두 번째 신호는 즉시 끝낸다.
  - **API 오류 차단:** 출력을 못 얻었고 오류 가운데 openai 오류 클래스가 있으면 그 실행을 완료로 치지 않는다. 기록한 뒤 바로 멈추고, 재개할 때 다시 돌린다.
  - **중간 확인:** `tashkeel exp002-status`와 진행 로그에는 진행 수, 토큰, 형식 실패·재시도·API 오류 수, 예상 총량·남은 시간만 보인다. 단가를 설정하면 추정 금액도 보인다. 비율 지표와 판정은 완료 뒤 `summary.json`에만 나온다.
    - 비용 때문에 그만둘 때만 `--finalize`로 부분 결과를 쓴다(`complete: false`).
- 선택 이유와 근거:
  - **기록 파일:** 산출 파일 유무로 판단하면 쓰다가 끊긴 실행을 완료로 볼 수 있다. 기록 파일은 산출 파일을 다 쓴 뒤에 한 줄을 남기므로 그 문제가 없다.
  - **순서:** 반복 1회(120회)가 끝날 때마다 네 조건이 같은 문서로 채워진다. 비용 때문에 2회에서 멈춰도 균형 잡힌 결과가 남고, API 쪽 시간 변화도 조건에 고르게 걸린다.
  - **동시 실행:** 실행 하나의 시간 대부분이 API 응답 대기라 동시 실행으로 시간이 줄고, 토큰과 비용은 그대로다. 실행 사이에 공유 상태가 없어 결과도 같다(가짜 모델로 workers 1과 3의 summary가 같음을 테스트로 확인).
  - **버린 대안:**
    - Batch API: C2의 툴 호출 루프와 맞지 않고 오히려 느리다.
    - 추론 강도 낮추기: 실험하는 모델 조건 자체가 바뀐다.
    - 반복 축소: 사용자가 확정한 규모다.
    - 로컬 모델: 이 Mac(16GB)에서는 8B급까지만 돌아 아랍어와 스키마 출력이 약할 것으로 보이고[가설], 더 느리다. 제품 모델에 대한 결론으로 옮겨 쓸 수 없다. 사용자도 gpt로 하기로 했다.
  - **중간 확인:** 중간 결과를 보고 멈출지 정하면 사전 등록한 판정(C1 합격 시 중단)이 선택적 중단으로 흔들린다. 사용자도 사용량·진행만 보기로 했다.
- 비용·성능·구조에 미치는 영향:
  - 그래프·채점·집계·판정 코드(`graph.py`, `reconcile.py`, `aggregate`·`compare`·`judge`·`PASS_BAR`)는 그대로다. 골든 테스트가 바뀌지 않았다.
  - `summary.json`에 `run_dir`·`complete`·`n_runs_done`·`n_runs_planned`·`sessions`·`api_error_runs`·`pauses`가 더해졌다.
  - `Settings`에 `price_input_per_mtok`·`price_output_per_mtok`(선택)가 더해졌다.
  - 동시 실행 4개면 dev 점검 기준으로 360회가 약 1.4~1.9시간이다[추정]. 예산 제한은 돌던 실행만큼(최대 workers − 1개) 넘칠 수 있다.
  - 강제 종료로 끊긴 실행의 사용량은 기록되지 않는다. 청구 기준은 OpenAI 대시보드다.
- 재검토 조건:
  - 계정 한도 때문에 429로 자주 멈출 때 → workers 조정.
  - EXP-002 결과가 반복 회차 사이에 체계적으로 다를 때 → 시간 변화 의심.
  - 단계 1.5 서비스에서 같은 작업 실행 방식을 쓰게 될 때.
- 관련 코드·실험·트러블슈팅:

  - 테스트: `tests/test_exp002_resume.py`
  - 실험: EXP-002
