# ADR-019 — 완제품 패키지: API 키 인증과 고객 분리, 멀티 에이전트 틀(M1, 플래그), 화면에서 대상 지정(제안만), Docker Compose 전달

- 날짜: 2026-10-21
- 상태: 채택(구현). M1은 ADR-021에서 보류했다가 ADR-022가 기본 경로(M2)로 넓힘
- 배경: 사용자가 "실험은 잘 됐다 치고 완제품부터 만들자"고 했다. API·화면·Postgres·MCP는 있었지만 인증과 고객 분리가 없었다(`customer_id`가 자유 문자열). 판매 형태 후보인 멀티 에이전트는 설계 전이었고, 실무자가 서류를 넣으려면 JSON을 써야 했으며, Docker Compose는 띄워 본 적이 없었다.
- 결정: API 키 인증과 고객 분리, 멀티 에이전트 틀 M1(플래그), 업로드 화면에서 대상 지정(제안만), Docker Compose 패키지를 만든다.
- 결정 이유: API 키는 판매 형태(API)에 맞고 구현이 작다. 고객 + 묶음 ID 유일 키가 아니면 고객끼리 묶음 ID가 충돌해 남의 결과를 덮어쓴다. M1을 `CONDITIONS`에 넣으면 실험 계획·골든·해시가 모두 바뀐다. 중재자를 규칙으로 두면 "근거 없이 확정하지 않는다"(G2)를 코드로 보장하고 비용이 들지 않는다. 자동 연결은 ADR-018이 금지한 "이름이 같으면 같은 대상"이다.
- 고려한 대안: (인증) OAuth·세션 로그인 / 인증 없음. (분리) 묶음 ID 전역 유일. (멀티 에이전트) M1을 `CONDITIONS`에 추가 / LLM 중재자 / 다른 서류 근거를 `AgentOutput`에 인용하도록 스키마 확장. (대상 지정) 같은 아랍어 표기 자동 연결. (전달) 클라우드 배포까지.
- 최종 결정:
  - 인증: `customers` 표, 키는 `tk_` + 무작위 48자이고 발급 때 한 번만 평문으로 보이며 sha256만 저장한다(`tashkeel customers add|list|revoke`). 요청은 `X-API-Key` 또는 Bearer, SSE는 `?api_key=`로 받는다. `AUTH=auto|required|disabled`. 묶음·작업·사전은 키의 고객에 묶이고 `bundles` 유일 키는 `(customer_id, bundle_id)`다. `usage` 표와 `GET /v1/usage`로 사용량을 본다.
  - M1: `ENGINE_CONDITIONS`에 두고 `MULTI_AGENT=true`일 때만 받는다. agent 노드만 번역자 → 격리 검증자 → 규칙 중재자로 바뀐다. 둘 다 근거 채택이고 철자가 정확히 같고 둘 다 근거 검증을 통과할 때만 확정한다. 다른 서류의 근거는 참고로만 준다.
  - 대상 지정: `POST /v1/bundles/draft`가 이름 칸과 묶음 제안을 돌려주고(저장 안 함), 사람이 눌러야 대상이 된다.
  - 전달: Docker Compose(앱 + Postgres), `docs/deploy.md`, `scripts/smoke.sh`. 클라우드·TLS·리버스 프록시는 넣지 않는다.
  - 범위 밖: PDF·DOCX·스캔본, pgvector 이전, M1 비교 실험과 실제 모델 실행, SOC 2.
  - 영향: M1은 LLM 호출이 2회라 비용이 약 2배다. Alembic 0003. 화면은 API 키를 localStorage에 둔다.
  - 재검토: 고객이 여러 사용자·권한을 요구할 때, M1이 단일 에이전트보다 낫지 않을 때, 제안 그룹이 자주 틀릴 때.
