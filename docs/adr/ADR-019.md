# ADR-019 — 완제품 패키지: API 키 인증과 고객 분리, 멀티 에이전트 틀(M1), 화면에서 대상 지정, Docker Compose 전달

- 날짜: 2026-10-21
- 상태: 채택(구현 중)
- 배경과 문제: 사용자가 "실험은 잘 됐다 치고 완제품부터 만들자"고 했다(2026-10-21). 문서가 정한 최종 결과물은 "아랍어 서류 묶음을 받아 이름별 확인 대기 목록을 근거와 함께 돌려주는 API"(ADR-009: KYC·컴플라이언스 팀에 API로 판매, 체험용 셀프서브 화면, MCP 부품)다. 단계 1.5(ADR-012)와 단계 2(ADR-018)로 API·화면·Postgres·MCP는 있지만, 인증과 고객 분리가 없고(`customer_id`는 호출자가 적는 자유 문자열), 판매 형태 후보인 멀티 에이전트(단계 3)는 설계 전이며, 실무자가 서류를 넣으려면 JSON을 써야 하고, Docker Compose는 한 번도 띄우지 않았다.
- 사용자 결정(2026-10-21): (1) 멀티 에이전트도 틀까지 만든다(비교 실험은 나중). (2) 전달 형태는 Docker Compose 패키지 + API 키, 클라우드 배포는 안 한다. (3) 실무자는 업로드 화면에서 대상 ID를 지정한다. PDF·DOCX는 안 한다.
- 검토한 대안:
  - (인증) API 키 헤더 / OAuth·세션 로그인 / 없음(지금). 고객 분리는 묶음 ID를 전역 유일로 두고 충돌 시 거부 / 고객 + 묶음 ID로 유일.
  - (멀티 에이전트) 조건 `M1`을 기존 `CONDITIONS`에 추가 / 별도 `ENGINE_CONDITIONS`로 두고 플래그로 노출. 중재자를 LLM으로 / 규칙 함수로. 다른 서류의 근거를 `AgentOutput`에 인용 가능하게 스키마 확장 / 참고로만 주고 교차 확정은 묶음 규칙이.
  - (대상 지정) 서버가 같은 아랍어 표기를 자동으로 같은 대상으로 연결 / 제안만 하고 사람이 고른다.
  - (전달) Compose 패키지 / 클라우드 배포까지.
- 결정:
  - **인증·분리·사용량:** `customers(id, name, api_key_hash, key_prefix, active …)` 표. 키는 `tk_` + 무작위 48자, 발급 때 한 번만 평문으로 보이고 sha256 해시만 저장한다(`tashkeel customers add|list|revoke`, DB 직접). 요청은 `X-API-Key` 또는 `Authorization: Bearer`, SSE는 `?api_key=`(접근 로그에 남는 한계를 문서에 적는다). 없거나 틀리면 401 `kind:"auth"`. 인증된 요청의 묶음·작업·사전·목록은 키의 고객에 묶이고, 본문의 `customer_id`가 키의 고객과 다르면 400이다. `bundles` 유일 키를 `(customer_id, bundle_id)`로 바꿔 다른 고객이 같은 묶음 ID를 써도 따로 저장한다. `usage` 표에 작업마다 토큰·호출 수·구간 수를 남기고 `GET /v1/usage?from=&to=`로 고객이 본다. `AUTH=auto`(기본)는 고객이 하나라도 있으면 인증 필수, 없으면 지금처럼 열림. `required` / `disabled`도 둔다.
  - **멀티 에이전트 틀:** 조건 `M1`은 `ENGINE_CONDITIONS`에 두고 `CONDITIONS`(C0~C3)는 건드리지 않는다(실험 계획·골든·해시 열거가 묶여 있어서). `agent` 노드만 하위 그래프(번역자 → 격리 검증자 → 규칙 중재자)로 바뀌고 나머지 노드·채점·골든 테스트는 그대로다. 검증자는 번역자 출력을 보지 않는다. 중재자는 LLM이 아니라 규칙 함수다: 둘 다 근거 채택이고 철자가 정확히 같고 둘 다 근거 검증을 통과할 때만 확정, 아니면 보류(사유 코드 기록). 다수결·근거 생성은 없다. `MULTI_AGENT=true`일 때만 API·화면에서 `M1`을 받는다. 다른 서류의 근거 표기는 **참고**로만 준다. `AgentOutput`의 근거는 문서 안 구간이라(스키마 해시 고정, `reconcile.verify_evidence`도 문서 안만 검증) 교차 서류 확정은 지금처럼 `bundle/rules.decide_status`가 한다.
  - **화면에서 대상 지정:** `POST /v1/bundles/draft`가 올린 파일에서 이름 칸을 뽑아 "서류/구간/칸/값"과 묶음 **제안**을 돌려준다(저장 안 함, `entity_id` 없음). 같은 아랍어 표기는 같은 그룹으로 제안만 하고, 사람이 "제안대로 만들기"를 눌러야 대상이 된다(ADR-018의 "ID를 추측하지 않는다"를 지킨다). 검수는 화면이 조립한 JSON으로 기존 `POST /v1/bundles/review`를 쓴다.
  - **전달:** Docker Compose(앱 + Postgres), `.env`의 `POSTGRES_PASSWORD`·`OPENAI_API_KEY`·`AUTH`, healthcheck, 첫 실행에 `docker compose run --rm app tashkeel customers add`, `docs/deploy.md`, `scripts/smoke.sh`. 클라우드 배포 설정·TLS·리버스 프록시는 넣지 않는다.
  - **범위 밖:** PDF·DOCX·스캔본, 벡터 검색의 pgvector 이전, 멀티 에이전트 비교 실험과 실제 모델 실행, SOC 2·개인정보 검토, 서류 종류별 우선순위.
- 선택 이유와 근거: API 키는 판매 형태(API)에 맞고 구현이 작다. 고객 + 묶음 ID 유일 키가 아니면 고객끼리 묶음 ID가 충돌해 남의 결과를 덮어쓴다. `M1`을 `CONDITIONS`에 넣으면 `--condition all`·실험 계획 수·골든 160건·프롬프트 해시 핀이 모두 바뀐다. 중재자를 규칙으로 두면 "근거 없이 확정하지 않는다"(G2)를 코드로 보장하고 비용이 안 든다. 자동 연결은 ADR-018이 금지한 "이름이 같으면 같은 대상"이라 제안까지만 한다.
- 비용·성능·구조에 미치는 영향: 단일 문서 경로·실험·골든·해시는 바뀌지 않는다(테스트로 고정). M1은 LLM 호출이 2회라 비용이 약 2배이고 형식 재시도 시 둘 다 다시 돈다. `BundleStore`·`JobManager` 조회 함수에 고객 범위 인자가 생긴다. Alembic 0003(customers, usage, jobs.customer_id, bundles 유일 키 변경). 화면은 API 키를 브라우저 localStorage에 둔다.
- 재검토 조건: 고객이 여러 사용자·권한을 요구할 때(조직·권한 모델). M1 비교 실험에서 말없이 찍는 비율이 단일 에이전트보다 낮지 않을 때(단일 에이전트 API로 판매). 실제 묶음에서 제안 그룹이 자주 틀릴 때.
- 관련 코드·실험·트러블슈팅: `web/auth.py`, `web/customers.py`, `web/usage.py`, `alembic/versions/0003_customers_usage.py`, `multi_agent.py`, `bundle/draft.py`, `docker-compose.yml`, `docs/deploy.md`, `scripts/smoke.sh`, `docs/과제2-테스트-기록.md` 6절.
- 대체하거나 대체된 ADR: ADR-009(판매 형태)·ADR-012(단계 1.5)·ADR-018(묶음 검수)을 보완한다. 단계 3의 "비교 뒤 판매 형태 결정"(roadmap)은 그대로이고, 이번에는 틀만 먼저 만든다.
