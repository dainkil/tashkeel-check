# ADR-015 — EXP-001 개발용 표본에서 표기 일치·정렬 규칙을 v1로 고쳐 고정하고, dev 분할을 키 목록으로 고정하며, 합성 문서를 다시 만든다

- 날짜: 2026-10-20
- 상태: 채택
- 배경과 문제: EXP-001은 dev 300개로 정렬·일치 규칙을 고친 뒤 고정하고 main을 한 번 재도록 사전 등록했다([6.1절](../evaluation.md)). dev를 돌려 단위를 하나씩 보니 세 가지가 드러났다. (1) 일치 규칙 v0는 5자 이상이면 편집 거리 1을 같은 이름으로 봤다. 그래서 Hajjaj ↔ hujaj, Al Bashri ↔ al-bashariyy, Jamaan ↔ jum'an, Rostam ↔ rustum처럼 모음이 다른 독법이 일치로 들어갔다(약 16건). 이 프로젝트가 구별하려는 Muslim·Musallam, Hamad·Hamd와 같은 종류의 차이다. (2) 영문 표기 관례를 읽지 못했다. عبد X 9개가 전부 불일치였고(Abdul ↔ 'abd al-), ظ·ذ·ض의 th·dh(Hafith, Dhaif), 이중모음 o·ou(Touqi), 타 마르부타의 -eh(Hamadeh), آل의 aal도 놓쳤다. (3) 정렬이 라틴 문자로 된 아랍어 레이블(Khaleghian ↔ Manager)과 접두가 한쪽에만 있는 별칭(إبراهيم ↔ Abu Aws, عبد الفتاح ↔ Ali)을 받아들였다. M5(0.58)가 판단 기준선(0.5)에 가까워 이 오차가 판정을 바꿀 수 있었다. 또 dev·main 분할이 단위 목록의 위치로 정해져, 정렬 규칙을 바꾸면 이미 본 dev 단위가 main으로 넘어갈 수 있었다.
- 검토한 대안: (일치) 편집 거리를 유지하고 예외만 더한다 / 편집 거리를 없애고 정규화만 쓴다 / 모음은 같아야 하고 자음 쪽 차이만 허용한다. (분할) 위치 기반 유지 / 키 해시 임계값으로 새로 나눈다 / v0 dev 키 목록을 파일로 고정한다. (합성 문서) 그대로 두고 잘못된 짝을 알려진 잡음으로 적는다 / 이름 풀을 v1로 다시 만들어 다시 생성한다.
- 결정: 일치 규칙 v1. 관사(al·el·ul·aal)와 하이픈·아포스트로피를 걷고, 붙여 쓴 Abdul·Abdel·Abdur를 abd로 줄이고, 영문 e는 a·i·u, o·ou는 u·aw로 펼친다(영문에만 나오는 글자라 아랍어 로마자 쪽은 펼쳐지지 않는다). th·dh·z·d를 한 부류로, q와 k를 같게 본다(방언 옵션은 q ↔ g를 더한다). 겹글자를 접고, ay를 ai로, 끝 -iyy를 -i로, 끝 -ah를 -a로 둔다. 정규형이 같으면 일치이고, 아니면 대표형(e → i, o → u)끼리 자음 하나를 더하거나 빼거나 y ↔ i·w ↔ u 하나만 바꾼 차이일 때만 일치로 본다(4자 이상). 정렬 규칙 v1은 [5.1절](../data.md). dev는 v0 단위 목록의 seed 7 앞 300개 키를 `data/wikidata/exp001_dev_keys.json`에 고정하고 `split_by_keys`로 나눈다. 이름 풀을 v1로 다시 만들고 합성 문서를 synthetic-v2로 다시 생성한다.
- 선택 이유와 근거: 독법 차이는 모음 차이다. 편집 거리는 모음과 자음을 구별하지 않아 이 프로젝트의 측정 대상을 지운다. 영문 e는 Ahmed(a)·Hamed(i)·Yousef(u)처럼 셋 다 되므로 펼쳐야 흔한 표기를 놓치지 않는다. 자음 쪽 차이는 같은 아랍어 철자에서 나온 후보끼리는 독법을 바꾸지 않는다. 펼친 변형에 한 글자 허용을 겹치면 o → aw → a가 되어(Obadah ↔ 'abbadah) 대표형끼리만 허용했다. 아인 양옆의 모음을 합치지 않는 규칙도 시험했지만 Al Zaabi ↔ al-za'abiyy처럼 흔한 표기를 놓쳐 버렸다. 키 목록 고정은 규칙을 바꿔도 dev 구성이 그대로이고, 빠지는 단위만 생긴다(라틴 문자 레이블 2개). 합성 문서는 v1에서 걸러지는 짝이 eval 정답 표기 4토큰에 들어가 있었고, eval로 아무것도 돌리지 않았으므로 다시 만드는 비용이 낮다.
- 비용·성능·구조에 미치는 영향: EXP-001 dev M5가 엄격 0.58 → 0.587, 방언 허용 0.58 → 0.591이 되었다(오일치 약 16건이 빠지고 놓친 일치 17건이 들어옴). `match_spelling`은 EXP-002 채점(근거 인용 검사, 보류 후보 적중, C0 표기 찾기, 표기 일관성)과 단계 2 묶음 검색에도 쓰인다. 같은 dev 문서로 골든을 다시 만들어 비교하니 160건 모두 `matcher_version`만 바뀌었다. 합성 문서는 이름이 바뀐 문서가 dev 8개, eval 21개이고, 근거 배치와 개수(eval 근거 없는 이름 61개, 토큰 174개)는 그대로다. 골든을 다시 만들었고, 사용자 메시지 해시만 갱신했다. 프롬프트·출력 스키마·툴 스키마는 그대로다. 비교 비용이 영문 e·o 개수에 따라 늘어 변형 수를 256개로 제한하고 결과를 캐시한다.
- 재검토 조건: main 측정 뒤 오일치·불일치 표본을 사람이 볼 수 있게 될 때. 공개 이중언어 문서 측정(단계 2)에서 영문 표기 관례가 다른 지역(레반트·남아시아)이 많을 때. 영문 e 펼침이 EXP-002의 보류 후보 적중률을 부풀린다는 근거가 나올 때.
- 관련 코드·실험·트러블슈팅: `romanize.match_spelling`·`normalize_latin`·`canonical_latin`, `data/names.py`(`plausible_pair`·`_prefix_consistent`), `experiments/exp001.split_by_keys`, `tashkeel fetch-wikidata --pool-only`(재조회 없이 이름 풀만 다시 만듦, 두 번 만들어 같은 파일임을 확인), `data/wikidata/exp001_dev_keys.json`, `data/synthetic.py`(`GENERATOR_VERSION`), `tests/test_text_romanize.py`·`test_names.py`·`test_experiments_code.py`, EXP-001, EXP-002
- 대체하거나 대체된 ADR: 없음. 6.1절의 사전 등록(dev로 규칙을 고친 뒤 고정)을 따랐다. ADR-014의 합성 문서 구성(근거 배치)은 그대로다.
