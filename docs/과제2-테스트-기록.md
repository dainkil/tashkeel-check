# 과제 2 테스트 기록 — 단계 1.5 서비스(API·화면·DB·MCP)

- 작성: 2026-10-21. 실행한 것만 적는다. 모델은 가짜 모델(`LLM_BACKEND=fake`)이고, 실제 모델 실행은 EXP-002가 끝난 뒤에 한다(아래 "하지 않은 것").
- 환경: macOS, Python 3.11.15, uv, camel-tools 1.6.0 + calima-msa-r13, Postgres 17(Homebrew, 로컬 소켓 `postgresql+psycopg:///tashkeel`), fastapi 0.156, fastmcp 4.1, mcp 2.3, sqlalchemy 2.1, alembic 1.20.
- 자동 테스트: `tests/test_web_api.py` 15개(그중 `db` 마커 1개), `tests/test_mcp.py` 10개(그중 `camel` 마커 2개), `tests/test_graph_fake.py`에 `on_node`·`analyze_tool_factory` 2개. 단계 2 묶음 검수(2026-10-21, 5절): `tests/test_bundle_*.py` 8파일 94개(그중 `db` 1개). 전체 `uv run pytest -m "not live"` 372개 통과·3 skip(DATABASE_URL 있음). 골든 160건 변화 없음.
- 화면 캡처: `docs/images/`.

## 1. 실행 방법 (Mac)

```bash
uv sync && uv run camel_data -i morphology-db-msa-r13
createdb tashkeel                                   # 또는 docker compose up db
cp .env.example .env                                # LLM_BACKEND, DATABASE_URL, USE_MCP_TOOLS를 넣는다
LLM_BACKEND=fake USE_MCP_TOOLS=true DATABASE_URL=postgresql+psycopg:///tashkeel ./run.sh
```

`run.sh`는 키·포트를 검사하고 `alembic upgrade head`를 돌린 뒤 `uv run tashkeel serve`를 띄워 `/health`를 기다린다. 화면 `http://127.0.0.1:8000`, API 문서 `/docs`.

## 4. 하지 않은 것

- 실제 모델(`LLM_BACKEND=openai`) 실행. EXP-002 eval이 같은 API 키로 돌고 있어 끝난 뒤 dev 문서 1개로 1회 실행해 여기에 적는다.
- 분석기 로드 실패 기동 거부: camel DB가 설치된 환경이라 재현하지 않았다. 코드 경로는 `build_runtime` → `thread_safe_analyze()` → `AnalyzerUnavailable(ConfigError)`로 E-5와 같다.
- `docker compose up` 전체 기동. `Dockerfile`·`docker-compose.yml`은 작성만 했고 이미지를 빌드하지 않았다[미확인].

## 8. 조건 M2: 두 agent + 회사 기록(MCP) + 회사 문서 보관함 (2026-10-22, ADR-022)

### 8.4 하지 않은 것

- **정확도·비용·시간 측정**(EXP-005 [제안]). M2가 단일 문서에서 C1보다 나은지 나쁜지, 보관함 제안이 맞는 비율과 이름이 같은 다른 대상을 잘못 제안하는 비율을 모른다. 합성 보관함 사례 데이터도 만들지 않았다. 8.3의 두 회는 작동 확인이다.
- 실제 모델로 화면 확인(8.1은 가짜 모델), Postgres 보관함에 실제 OpenAI 임베딩을 넣은 실행(Postgres는 연습용 임베딩으로만 테스트).
- 외부 MCP 클라이언트용 `/mcp` 공개(사용자 결정으로 미룸).
- 연습 모드의 보관함 후보 고르기는 첫 자음 대응만 보는 흉내다. 실제 판단이 아니다.
- 화면에서 실제 로컬 파일 선택·끌어 놓기(7.3과 같은 이유).

### 8.5 화면 이름 상태를 세 가지로 (2026-10-22)

사용자 결정으로 결과 화면의 이름 색을 다섯(주황 보류, 보라 보관함 제안, 초록 문서 근거 확정, 파랑 사전 확정, 빨강 사전과 문서가 다름)에서 셋(초록 확정, 주황 확인 필요, 빨강 사전과 문서가 다름)으로 줄였다. 화면(`web/static/index.html`)만 바꿨고 API 결과의 상태 값과 검수 로직은 그대로다. 세부 상태(근거가 문서인지 사전인지, 지난 서류 후보가 있는지)는 이름을 누르면 패널 머리에 나온다.

**실제 모델에서 본 문제 (미해결, 2026-10-22).** 스크린샷을 다시 찍으려고 샘플 dev_005를 실제 모델(M2)로 한 번 돌렸다(형식 통과, 오류 0, 59초, 토큰 10.4k, LLM 호출 4). 번역 agent는 이름을 단어별로(`نوال`, `معمر`, `النجعي` …) 냈고, 검증 agent는 전체 이름 두 개(`نوال معمر النجعي`, `جمعان بن جبران بن بشار العابد`)만 냈다. 중재자는 토큰 묶음이 같은 항목끼리만 짝을 지으므로, 전체 이름 두 개가 "검증 agent만 찾은 이름"(`verifier_only`)으로 보류 항목에 더해졌다(요약 "이름 10"). 화면은 한 토큰을 마지막 이름 항목이 차지하게 칠하므로 전체 이름 항목이 단어별 항목을 덮는다. 그래서 `نوال`을 누르면 전체 이름 패널(`Nawal Muammar Al Naj'i`)이 열리고, 번역문의 `[Nawal/Nawaal]`에 해당하는 단어별 항목은 누를 수 없다. 여기서 전체 이름을 확정하면 사전 키가 전체 이름이 되어, 번역문 치환과 다음 서류의 단어별 재사용이 맞지 않는다. 그래서 스크린샷 재촬영은 멈췄다. 고칠 방향은 사용자와 정한다.
