## 2. 전체 계획에서의 위치

원칙: **기능은 적게, 측정은 많이.** 단계 1의 단일 에이전트는 제품 시제품이 아니라 [1.3절](problem-and-goals.md) 질문에 답하는 실험 장치이고, 단계 3에서 멀티 에이전트 구조를 정당화할 때 비교 대상이 되는 베이스라인이다.

| 단계 | 내용 | 사업 검증 순서와의 관계 |
| --- | --- | --- |
| 1 (지금) | Q0 실측 + 단일 에이전트 실험 장치(조건 C0~C3) | 사업 판정의 첫 관문. EXP-001이 이름 후보 열거 성공률을, EXP-002가 무료 LLM 대체 위험(지시만으로 충분한가)을 잰다 |
| 1.5 (과제 2 서비스화, 2026-10-21 구현) | 단일 문서 검수 웹 화면 + API + Postgres 저장 + 최소 MCP(툴·리소스·프롬프트). 같은 그래프를 서비스 경로에서 호출할 뿐, 실험 설계와 단계 1 코드는 바뀌지 않는다(ADR-012) | 과제 2 결과물. 단계 2 API·화면(M4)의 단일 문서 부분집합을 앞당긴 것이고 사업 판정과는 무관하다 |
| 2 (묶음 검수, 2026-10-21 첫 구현) | 서류 묶음 근거 검색(같은 대상 ID의 다른 서류), 확정/대기 판정, 표기 사전, 묶음 API·화면 탭, MCP `search_bundle`. 합성 묶음 사례(9 × 3종류)로 테스트. 14단계 가이드를 레포에 얹은 것(ADR-018). EXP-002 보류 중에 사용자 결정으로 먼저 함 | 사업 판정(EXP-002)과는 독립. 사람 검토는 추후 과제(ADR-008, ADR-009). KYC 묶음 생성기·pgvector·업로드는 남음 |
| 3 | 멀티 에이전트(번역자 / 격리된 검증자 / 중재자)를 단계 1과 같은 지표로 비교. 나으면 판매할 형태가 된다 | 단계 2 이후. "독립된 두 번째 확인"이라는 판매 문구는 이 비교가 통과해야 쓴다(ADR-009) |
| 별도 | 문자 인식(스캔본) 오류 측정 | 모음 기인 오류와 섞이지 않게 따로 |

주요 기능 선정(F1~F14), 기술 스택·시스템 구성(API 초안 포함), 마일스톤 M0~M6은 [docs/roadmap.md](roadmap.md)에 있다. 요약: 제품은 "서류 묶음을 받아 이름별 확인 대기 목록을 돌려주는 API"이고, 스택은 단계 1 것에 FastAPI·Postgres(+pgvector)·Docker를 더하며, EXP-001·002 관문(약 3~4주) 통과 뒤 묶음 근거 검색 → API → 멀티 에이전트 비교 순으로 약 10~11주를 쓴다 [제안].

사업 검증 순서(중단 기준 기록 → EXP-001 → EXP-002 → 공개 이중언어 문서 측정 → UAE 번역료 재확인)는 사업성 검토 문서 "다음 순서"를 따른다. 인터뷰, 사람 검수를 쓰는 사전 감사, 무료 진단은 할 수 없어 추후 과제다(ADR-008).


## 3. 범위

### 단계 1에 넣는 것

- **입력:** 텍스트가 살아 있는 아랍어 문서(구간 단위로 나눌 수 있는 일반 텍스트). 스캔본은 뺀다. 문자 인식 오류가 섞이면 틀린 원인이 모음인지 인식인지 구분할 수 없다.
- **에이전트가 하는 일:**
  1. 아랍어 → 영어 번역
  2. 독법이 갈리는 구간마다 후보, 채택한 독법, 이유, 확신도를 내거나 기권
  3. 고유명사마다 로마자 후보, 채택 표기, 근거를 내고, 근거가 없으면 보류
- **도구:** 형태소 분석기(CAMeL Tools) 하나
- **측정:** [6절](evaluation.md) 지표 전부를 실행마다 기록

### 단계 1에서 뺀 것

필요해 보여도 추가하지 않는다.

- 스캔 PDF와 문자 인식
- 묶음 내 서류 검색, RAG, 벡터 DB. 같은 사람이 나오는 서류 묶음이 있어야 시험할 수 있는데 공개 자료로는 구하기 어렵다(ADR-003)
- 이름 사전(고객별 확정 표기 저장)
- 사람 검토를 위한 중단·재개(LangGraph interrupt). 보류 목록은 결과 파일로만 낸다
- 웹 화면(→ 단계 1.5로 이동, ADR-012. 실험 조건 C0~C3에는 여전히 영향 없음), 인증·보안, 한글 표기, 멀티 에이전트
- 번역 문장 품질 평가

### 정한 것 (2026-10-21, 사용자 확정, 서비스 정확도 99%와 어려운 시험지 — ADR-017)

- **배경:**
  - EXP-002 반복 1회에서 C1~C3가 모두 만점이었다. 시험지가 쉬워서라고 본다[가설].
  - 사용자는 EXP-002의 남은 240회를 보류하고, 아주 어려운 경우까지 넣은 새 시험지·답안지를 만들기로 했다.
  - "서비스 특성상 정확도는 99% 이상이어야 한다"(사용자).
- **99%의 정의:**
  - 이름 부분이 나올 때마다 센다.
  - 안전 정확도(말없이 틀린 이름이 없음)와 엄격 정확도(기대 처분과 정확히 일치)가 모두 0.99 이상이어야 한다.
  - 조건 비교 판정은 점추정으로 한다.
  - "서비스 기준 99% 달성"이라는 문구는 한쪽 95% 하한(반복마다의 Clopper–Pearson 중 최저, 문서 단위 부트스트랩)도 0.99 이상일 때만 쓴다.
- **시험지:**
  - synthetic-hard, 유형 17가지([5.3절](data.md)).
  - eval 70개 문서, 이름 부분 약 1,400~1,600개(별도 seed 시험 생성 범위). 유형별 값은 참고만 한다.
  - dev 20개.
- **지시문:** EXP-003에서는 p1을 쓴다. 규칙 4의 원칙(같은 사람의 표기만, 충돌하면 보류)만 분명히 하고 함정 유형은 나열하지 않는다. EXP-002는 p0 그대로다.
- **판정 구조:** EXP-002와 같다(C1 합격 → `stop`, 도구 조건만 합격하며 우연 이상으로 고침 → `pass`, 그 밖 → `fail`). 정의와 코드는 [6.4절](evaluation.md)과 `experiments/exp003.py`의 `PASS_BAR`·`judge`·`service_claim`이다.
- **근거:**
  - 99%는 사용자가 정한 서비스 요구다. 고객 인터뷰가 없어(ADR-008) 외부 근거는 없다.
  - 1,000개에서 하한이 0.99를 넘으려면 오류가 4개 이하여야 한다[계산].
- **EXP-002와의 관계:** EXP-002의 합격선(아래)은 바꾸지 않는다. 보류 상태로 두며, 99% 기준은 EXP-003에만 쓴다.

### 정한 것 (2026-10-20, 사용자 확정, EXP-002 판정 — M0 항목 5)

- 합격선: 세 기준을 모두 넘어야 그 조건이 합격이다. (1) 몰래 정함 비율(근거 없는 이름을 말없이 찍거나 근거 없이 확정한 비율) 0.10 이하, (2) 그중 근거 없는 확정 비율 0.02 이하, (3) 근거 있는 이름의 근거 채택 검증 통과율 0.90 이상. 비율은 eval 30개 × 3회를 합쳐 계산한다
- 판정: C1(지시만)이 합격이면 **중단**("지시만으로 충분", 단독 제품 대신 공개 벤치마크·연구 산출물로 마무리). C1이 불합격이고, C2나 C3가 합격하면서 C1이 못 넘은 기준마다 C1 − 도구 조건 차이의 95% 구간(같은 문서를 함께 뽑는 문서 단위 부트스트랩)이 도구 조건 쪽으로 0을 넘으면 **합격**(단계 2로). 그 밖에는 **불합격**(프롬프트 재설계 또는 단계 3 검토). C0는 판정에 쓰지 않고 Q1 결과로 보고한다
- 근거: 고객 인터뷰를 할 수 없어(ADR-008) 외부 근거가 없는 판단값이다. 0.10은 "확인되지 않은 이름 10개 중 1개 넘게 표시 없이 정하면 안 된다"는 뜻이다. 선을 느슨하게 하면 C1도 넘기 쉬워 중단 판정이 잘 나고, 엄격하게 하면 시험지 20개로는 판정 불가가 늘 수 있다 [추정]. 이전 제안("C1이 C2·C3의 반복 간 범위 안이면 중단")은 표본이 작을수록 충족되기 쉬워 버렸다
- 고정 방법: `experiments/exp002.py`의 `PASS_BAR`·`judge`로 코드에 두고 실행 전에 커밋했다. `summary.json`에 `verdict`로 나온다

### 정한 것 (2026-10-20, 사용자 확정, 과제 2 반영 — ADR-012)

- 기본 구조는 기존 계획대로 두고, 제공 ZIP(`all_total_vue_student/`)에서는 쓸 만한 패턴만 가져온다. ZIP 구조를 레포 루트에 복제하지 않는다.
- 웹 화면은 만든다. 챗봇 형태는 쓰지 않는다. 아랍어 텍스트를 붙여 넣으면 번역과 이름별 확인 대기 목록, 지표가 표로 나오는 폼 화면이다.
- 저장소는 Postgres(ADR-011 유지). ZIP의 SQLite 세션 저장소는 쓰지 않는다.
- LLM 층은 기존 LangChain `init_chat_model` + `create_agent` + `ToolStrategy`(ADR-006) 유지. ZIP의 httpx 직접 호출 방식과 Ollama 백엔드는 넣지 않는다. 가짜 모델은 서비스에서 명시적으로 켤 때만 쓴다(키가 없다고 조용히 가짜로 떨어지지 않음).
- 서비스 입력 범위는 단일 문서(단계 1과 같음). 묶음 업로드(F5~F7 전체)는 단계 2에 남긴다.
- 구현은 사용자가 다시 지시할 때 한다. → 2026-10-21 사용자 지시로 구현했다[확인]. `USE_MCP_TOOLS`는 플래그로 끼우되 기본은 끔(사용자 결정 2026-10-21). 기록은 [과제2-테스트-기록.md](과제2-테스트-기록.md).

### 정한 것 (2026-10-20, 사용자 확정)

- 사업 구조(ADR-008): 영어-아랍어만 본다. 한국 고객·채널·한국어 출력은 뺀다. 고객은 번역가를 부르던 비용을 아끼려는 걸프(사우디·UAE) 영어권 최종 사용자이고, 번역사무소는 고객이 아니다.
- 인터뷰와 사람 검수(제품 안의 검수, 아랍어 검수자를 쓰는 사전 감사)는 할 수 없다. 추후 과제로 두고, 사업 판단은 공개 자료 추정과 자동 측정으로 한다.
- 판매 대상과 형태(ADR-009): 1순위는 걸프 법인 고객을 받는 은행·핀테크·결제사의 KYC·컴플라이언스 팀이고, API로 판다. 2순위는 걸프 진출 외국 중소기업 셀프서브 웹(체험·유입용)이다. 단일 에이전트는 중간 단계이고, 판매할 형태는 격리된 검증 에이전트를 둔 멀티 에이전트 API다(단계 3 비교 뒤). 이 프로젝트는 미니 프로젝트용으로 이어서 갱신한다.

### 정한 것 (2026-10-13, 사용자 확정)

- LLM: OpenAI. 기본 모델 `openai:gpt-6.1-sol`, `.env`의 `MODEL`로 바꾼다(ADR-006)
- EXP-001 판단 기준: M5(방언 허용) 50% → 2026-10-20 main 결과 0.502로 통과(여유 거의 없음, [6.1절](evaluation.md))
- 고확신 무근거 확정 기준: 확신도 0.8
- EXP-002 규모: 평가 문서 30개 × 반복 3회(개발 문서 10개는 디버깅용)
- RAG·벡터 DB: 단계 2용 틀만 만들고 단계 1 조건에는 붙이지 않는다(ADR-007)

### 확인한 것 (2026-10-20, M0 항목 3)

- `temperature`: `gpt-6.1-sol`은 0을 받지 않는다(400 `unsupported_value`, "Only the default (1) value is supported") [확인]. `TEMPERATURE`는 설정하지 않고 모든 실행이 기본값 1로 돈다. 같은 입력에도 결과가 실행마다 달라질 수 있으므로, 실행 간 변동은 6.2절의 반복 간 일치율로만 본다

### 확인한 것 (2026-10-21, EXP-002 dev 점검)

- 실제 모델(`gpt-6.1-sol`)로 dev_001(synthetic-v2)을 C0~C3 각 1회 돌렸다. 네 조건 모두 첫 시도에 형식 통과 [확인]. C0·C3를 실제 모델로 돌린 첫 실행이다. 실행당 토큰은 C0 0.6천, C1 6.3천, C2 13.0천, C3 19.2천이다. 이를 바탕으로 EXP-002 비용 추정을 약 $15~20으로 고쳤다(단가는 제3자 집계 값, [EXP-002 기록](experiments/EXP-002.md))
- 실행 방식: 동시 4개로 돌리고, 끊어 가며 진행하고, 중간에는 사용량·진행만 본다(사용자 결정, ADR-016). 규모·합격선·중단 기준은 그대로다

### 정한 것 (2026-10-21, 사용자 확정, 14단계 가이드 반영 — ADR-018)

- 가이드는 이 레포에 얹는다(새 `app/` 프로젝트 없음). EXP-002는 120/360에서 보류. 저장은 Postgres 유지. 멀티 에이전트(가이드 13단계)는 이번에 하지 않는다.
- 같은 대상 여부는 데이터의 대상 ID(`entity_id`)로만 판단한다. 확정은 정확 일치(대소문자·공백만 무시)일 때만이다. 사전은 사람이 대기 항목을 닫을 때만 등록한다.
- 고유명사를 어디까지 다루는가(사람 이름에 치중하지 않는다):

| 범위 | 무엇 | 어떻게 |
| --- | --- | --- |
| 묶음 근거 검수(단계 2, 구현) | 묶음 데이터에서 **대상 ID(`entity_id`)가 붙은 모든 명명 대상**: 개인 이름(이름·가문명 포함), 회사·법인, 기관·단체·정부 부처, 그 밖에 ID를 붙여 준 당사자(선박명, 상표, 프로젝트명 등). 종류(`entity_type`: `person` / `organization` / `other`)는 표시·집계용이고 규칙은 같다 | 같은 묶음 안에서 같은 ID가 붙은 다른 서류의 영문 칸을 근거로 찾고, 인용을 검증하고, 정확히 일치할 때만 확정 |
| 단일 문서 검수(단계 1, 그대로) | LLM이 `proper_noun` 항목으로 뽑는 것: 개인 이름·가문명·회사명(프롬프트 규칙 3). 잘 알려진 지명은 직접 번역하고, 지명·기관명은 중립 토큰으로 지표에서 뺀다(ADR-014) | 문서 안의 라틴 표기만 근거로 쓰고, 없으면 보류. 이 범위와 동작은 바꾸지 않는다(골든 테스트) |
| 둘의 연결 | 단일 문서 경로가 뽑은 `proper_noun` 항목 가운데 대상 ID가 붙은 구간의 것 | 묶음 근거 검색으로 넘긴다. 라벨 칸이 있는 구간은 라벨 결과가 우선이다. 연결되지 않는 항목은 "대상 ID 없음"으로 대기 |
| 범위 밖 | 일반 단어, 숫자·날짜, 주소 전체, 직함, 묶음에 ID가 없는 고유명사 | 근거 검색 대상이 아니다. 비슷한 표기로 추측해 연결하지 않는다 |

근거 서류의 종류는 정하지 않는다(신분증·여권·상업등기·정관·이전 계약서·공문 등). 어느 서류를 더 믿을지는 범위 밖이고, 서류끼리 다르면 무조건 대기다.

### 정한 것 (2026-10-21, 사용자 확정, 완제품 패키지 — ADR-019)

- 실험은 끝난 것으로 치고 완제품부터 만든다. 최종 결과물은 "아랍어 서류 묶음을 받아 이름별 확인 대기 목록을 근거와 함께 돌려주는 API 서비스"이고, 체험용 웹 화면과 MCP 부품이 딸린다.
- 전달 형태: Docker Compose 패키지 + API 키 인증 + 고객별 데이터 분리 + 사용량 기록. 클라우드 배포는 하지 않는다.
- 엔진: 단일 에이전트(C2·C3)가 기본이고, 멀티 에이전트(번역자 / 격리 검증자 / 규칙 중재자)는 조건 `M1` 틀로 만들어 `MULTI_AGENT` 플래그로 켠다. 비교 실험은 나중이다.
- 실무자는 업로드 화면에서 "같은 대상"을 지정한다. 서버는 제안만 하고 자동으로 연결하지 않는다. PDF·DOCX·스캔본은 받지 않는다.
- 범위 밖: pgvector 이전, 서류 종류별 우선순위, SOC 2·개인정보 검토, 멀티 에이전트 실제 모델 실행.

### 정한 것 (2026-10-21, 사용자 확정, 방향 전환 — ADR-021)

- EXP-003 `stop` 판정 뒤 1순위 고객을 KYC 팀(ADR-009)에서 **걸프에 진출한 외국 중소기업이 아랍어 서류를 내부 검토용으로 읽는 경우**로 바꾼다. 여권·대상 ID 묶음 전제는 빠진다.
- 제품 한 줄: 어떤 문서를 넣어도 고유명사마다 읽기 후보를 근거와 함께 제시하고, 사람이 확정한 것만 회사 사전에 저장해 다음 문서에서 바로 확정한다.
- 넣는 것(2026-10-21 구현): 서비스 기본값 p1·C1, 회사 사전의 단일 문서 적용(덧씌움, 고객 + `"*"` 키), 파일 업로드(.txt/.md/.pdf/이미지)와 교체 가능한 OCR 백엔드(기본 none, 무료 API ocrspace), 두 페이지 화면(파일 넣기 → 결과, 이름을 눌러 후보 토글, 후보를 누르면 확정·저장).
- 뺀 것: 날짜·숫자·금액 보류, 자기 회사 표기 감시(로드맵 [제안]), 이중언어 어긋남, 기한 추적, 번역사 요청서, 아랍어 회신, 로컬 OCR 구현, 분석기 선택화, 사전 표기를 LLM 입력에 넣기, KYC 묶음·M1 추가 개발.
- 하지 않는 실험: 문자 인식 성능. 인식 오류와 독법 오류를 구분해 보고할 수 없다는 점을 한계로 적는다.
- 가짜 모델(`LLM_BACKEND=fake`)은 분석기가 모르는 토큰만 보류로 내므로 실제 샘플에서는 이름 항목이 거의 없다. 화면 체험은 실제 모델로 한다(dev 1개 약 $0.05).

### 정한 것 (2026-10-22, 사용자 확정 — ADR-022, ADR-021 일부 뒤집음)

- agent·RAG·MCP·멀티 에이전트를 실제 제품 경로에 넣는다. **서비스 기본 경로를 C1에서 조건 M2로 바꾼다**(`REVIEW_CONDITION`, 되돌리면 C1).
  - 조건 M2는 M1 틀(번역 agent → 격리 검증 agent → 코드 중재자)이다. 두 agent가 회사 기록 툴(MCP)을 직접 부른다.
- RAG 자료는 회사 문서 보관함(이 고객이 전에 올린 서류)이다.
  - 같은 철자가 다른 대상일 수 있으므로 "보관함 제안"으로만 보이고, 확정은 사람이 한다(ADR-018·ADR-010 유지).
  - 다루는 고유명사는 사람 이름, 회사·상호, 정부기관·단체 이름이다. 날짜·숫자·금액은 여전히 밖이다.
- 멀티 에이전트는 새 역할을 나누지 않는다. 기존 M1 틀에 도구를 더하고 두 역할을 동시에 돌린다.
- **실험은 빼고 완제품부터 만든다.**
  - 합성 보관함 데이터, EXP-005, dev 실측은 이번 범위에서 뺀다. M2의 정확도는 재지 않은 채로 기본값이 된다.
  - 실제 모델로는 작동 확인만 한다(성능 측정 아님).
- 외부 MCP 클라이언트용 `/mcp` 공개는 뒤로 미룬다. 회사 기록 서버는 내부 agent만 메모리 전송으로 쓴다.
- ADR-021의 "뺀 것" 가운데 "M1 추가 개발"은 이 결정으로 뒤집혔다. "사전 표기를 LLM 입력에 넣기"도 일부 바뀌었다: M2의 기록 툴이 사전 표기를 agent에게 보여 준다. 다만 확정은 여전히 그래프 뒤 사전 덧씌움이 한다.
- 가짜 모델(연습 모드)의 M2는 번역하지 않는다. 회사 기록(사전·보관함)에서 찾은 이름만 보류로 내므로, 보관함이 비어 있는 첫 서류에서는 항목이 없다.
- 같은 날 이어서 정한 것:
  - 결과 화면의 이름 색은 셋이다. 확정(문서 근거·회사 사전), 확인 필요(보류·지난 서류 후보), 사전과 문서가 다름. 세부는 이름을 누르면 패널에 보인다. 화면만 바꾸고 API 상태 값은 그대로다. 화면 상단의 상태 줄(모델·조건·DB)은 지운다(`/health`에는 그대로 있다).
  - **현재 산출물로 제출을 확정한다.** M2의 전체 이름·단어별 항목 겹침(TS-005)은 고치지 않고 알려진 한계로 둔다. README 사진은 색을 줄이기 전 화면 그대로 둔다.

### 아직 정하지 않은 것

- 외부 `/mcp` 공개 시점

- 단계 1 실험 기준은 모두 정했다. 단계 2의 묶음 근거 확정률 목표는 합성 KYC 묶음에서 정한다
- EXP-003의 반복 횟수와 참고 조건(C1+p0, 지시문 변경과 시험지 변경을 떼어 보기)을 넣을지는 eval 생성 뒤 비용을 다시 추정해 사용자가 정한다
